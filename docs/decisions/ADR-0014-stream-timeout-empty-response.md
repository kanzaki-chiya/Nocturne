# ADR-0014：流式超时与空响应的失败语义

- 状态：已接受
- 日期：2026-09-25

## 背景

流连接建立后可能始终没有事件，也可能在中途停止发送。原有流式契约没有时间上限；模型以 `stop` 结束却没有文本和工具调用时，Turn 还会误报 `done`。这两项都改变失败语义，按 [provider-api.md](../protocols/provider-api.md) 第 6 节记录决策。

## 决定

所有模型流（普通 Step 与摘要）经过同一计时包装。从请求开始等待首个事件，以及每两个事件之间，分别设可配置上限；超时抛出可重试的 `ProviderError(kind="timeout")`，并中止本次底层请求。Adapter 不自行重试。Agent Loop 仅在该次尝试尚未输出事件时按原有上限重试；部分输出后的超时保存部分结果并以 `provider_timeout` 结束。

`stop` 且无文本、无工具调用视为 Agent Loop 内部可重试的空响应错误；它不改变 `ModelStreamEvent` 或 `ProviderError.kind` 的公共类型。重试用尽后 Turn 以 `provider_empty_response` 结束。成功流的事件顺序不变。

## 后果

静默连接有确定的退出时间。已经送达的内容不会因超时而自动重放；可能迟到但仍有效的模型输出会触发超时，用户可调高阈值。

## 备选方案

在各适配器分别设置超时会使 FakeProvider 和摘要调用行为不一致；在输出后无条件重试会重复文字与工具调用，因此不采用。

## 修订

- 2026-10-03：事件间空闲上限的默认值由 120 秒改为 300 秒（`turn.idleTimeoutMs` 仍可调）。长推理模型（如 GPT-6 系 high 档）在两段推理摘要之间可能静默超过 2 分钟，ChatGPT 账号冒烟中一轮思考约 8 分钟后被误判为断线，中断轮的加密推理无法保留，「继续」只能从头再想。代价是真正断开的连接要多等到 5 分钟才报错重试。首事件上限仍为 30 秒。
- 2026-10-03：计时原先只认内容事件（文字、推理、工具调用），上游的开始信号被适配器丢弃，长上下文或推理模型在首个内容前常超过 30 秒，各服务商都频繁出现「等待首个流式事件超时」并整段重发。`ModelStreamEvent` 增加 `heartbeat`：适配器在 fetch 层观察上游，拿到响应头、读到任意字节（含 SSE 保活注释）都算存活，至多每秒发一次（AI SDK 的 `start-step` 要等首个内容事件才发，实测不能用），计时包装据此满足首事件等待、重置空闲计时，消费后不向下游转发，不算已输出，不影响重试规则。首事件上限因此只衡量连接是否建立。
