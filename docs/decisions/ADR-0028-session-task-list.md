# ADR-0028：会话任务清单工具与进度显示

- 状态：已接受（维护者 2026-09-29 确认）
- 日期：2026-09-29

## 背景

[v0.5 路线图](../roadmap/roadmap.md)要求模型在长任务中列出步骤、逐项更新状态，客户端显示进度，并在恢复会话时还原清单。当前内置工具没有任务清单；会话的唯一事实来源是追加式事件日志，`tool.completed` 已保存工具的结构化 `output`。上下文压缩可能省略旧工具结果，TUI 的普通屏幕模式也不能回改已打印的内容。因此清单既要能从日志重放，又要独立于被压缩的对话历史进入后续模型请求。

## 决定

### 1. 一个会话一份清单，由工具完整替换

新增内置工具 `todo_write`，仅用于需要分步骤跟踪的长任务；不要求每次对话都创建清单。输入为 `{ items: [{ text, status }] }`，`status` 仅取 `pending`、`in_progress`、`completed`。调用提交**完整的新清单**，原子替换当前清单；`items: []` 明确清空。顺序由数组决定，允许多个步骤同时进行；不增设步骤 ID、截止日期、优先级或独立清单文件。

输入最多 20 项，每项 `text` 去除首尾空白后须非空、至多 200 字符，不能含换行或控制字符；未知字段和非法状态拒绝。校验失败不改变清单。工具结果的 `output.items` 是经校验的完整清单，`modelContent` 是简短的更新确认。工具不读写工作区文件、配置或网络；`permissionSubjects` 返回空数组，仍经过正常的工具执行与 Hook 流程。其 `mutates: false` 表示不修改外部资源；`concurrencySafe: false` 避免并发更新的歧义。同一会话若先后有多次成功更新，以持久事件顺序中最后一次为准。

### 2. 复用工具完成事件作为唯一事实

不新增 `todo.updated` 事件或提高 `formatVersion`。只有 `name === "todo_write"`、`status === "ok"`、且 `output.items` 符合上述结构与边界的持久 `tool.completed`，才改变清单。权限拒绝、Hook 拒绝、输入错误、超时、中断、工具运行失败以及只有 `tool.started` 的调用都保留上一份清单。若日志写入失败，不把未持久化的结果当成当前状态。

`SessionState` 与 `SessionView` 都从同一事件规则派生当前清单；旧日志没有此类事件时为无清单。重放不依赖 `HistoryEntry` 是否保留结构化 `output`，也不靠扫描界面条目。普通工具结果事件仍保留在对话中，供核对每次变更；清单本身不另行持久化。子代理是独立会话，其清单不合并到父会话。

### 3. 压缩后仍向模型提供当前清单

Context Builder 接收折叠后的当前清单，作为有界的当前状态块放入模型请求，并计入上下文预算与 `ContextReport`；空清单不注入。该块不依赖历史里的 `todo_write` 结果，因此修剪、摘要、恢复会话后仍能看到最新状态。清单文本视为任务数据，不得覆盖系统、用户或项目指令。Agent Loop 只传入会话状态，不按工具名处理清单。

### 4. 客户端显示

TUI 在 `todo_write` 结果出现的位置显示该次快照和完成数 N/M：为避免多次更新刷屏，快照只列最近完成的一项及其后两项，其后的项折为隐藏项数，完整清单由全屏固定区承担；标题以清单进度代替工具名与参数，避免重复打印 JSON。全屏模式在对话视口与输入框之间固定显示当前会话的清单标题、完成数和逐项状态，使历史滚动后仍可见。固定区含边框最多占 10 行，清单过长时优先显示进行中的步骤（连同前一项作参照）及其后续步骤，并提示其后隐藏的项数；终端太矮时缩小或隐藏固定区，不挤占输入区或遮住对话；清空后撤去。普通屏幕 TUI 与 CLI 逐次打印清单快照，不尝试修改已经输出的文本。恢复会话时，全屏清单从 `SessionView` 重建；无颜色和窄终端仍以文字、状态符号区分，不能只靠颜色。旧版客户端未识别该工具时，现有通用工具结果渲染仍可工作。

## 验收

- 验证输入上限、空数组清空、整份替换与多次更新；失败、拒绝、中断及未持久化结果不改变旧清单。
- 验证会话重放与恢复、子会话隔离、修剪与摘要后的模型请求及预算报告；旧日志仍可读取。
- 验证全屏 TUI 的当前进度与历史快照、普通屏幕 TUI 和 CLI 的逐次输出，以及窄终端、无颜色显示。界面效果在 Windows Terminal 目视检查；会抢前台的 GUI 自动化事先询问用户。
- 实现时同步 [工具设计](../architecture/tools.md)、[Tool API](../protocols/tool-api.md)、[会话](../architecture/sessions.md)、[事件](../protocols/events.md)、[视图](../protocols/view.md)、[上下文](../architecture/context.md)、[TUI](../apps/tui.md)与[CLI](../apps/cli.md)。在隔离的 `NOCTURNE_HOME` 下运行仓库规定的离线检查，不读取或写入真实用户配置。

## 后果

清单随事件日志恢复，工具更新、模型上下文和客户端视图共用同一份事实；代价是旧清单需要随请求重新注入，消耗少量固定上限的上下文。历史中保留每次快照会增加日志体积，但每次最多 20 项，不引入第二套存储或同步机制。完成的清单会保留到模型显式替换或清空，适合在同一会话继续核对。

## 备选方案

未采用独立 `todo.json`：它会成为事件日志之外的第二份事实，恢复与崩溃处理更复杂。未新增专用事件：现有 `tool.completed` 已能承载成功结果，再加事件会产生两种需要保持一致的记录。未从摘要或历史工具文本推断当前清单：压缩会丢失旧内容，文本也无法可靠区分成功与失败。
