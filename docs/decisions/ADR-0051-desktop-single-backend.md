# ADR-0051：桌面端改为单后台——一个 nctrn 后台服务所有项目，工作区随会话

- 状态：已接受（维护者 2026-10-07 确定改为单后台）
- 日期：2026-10-07
- 修订：[ADR-0046](ADR-0046-desktop-tauri.md) 第 1 节「一个项目一个后台，打开会话时才启动」及备选方案中「一个后台服务所有项目」的否决理由

## 背景

ADR-0046 让每个有打开会话的项目各起一个 `nctrn rpc --stdio` 后台，外加一个以普通对话工作区为 cwd 的常驻后台（ADR-0046 修订「启动即有一个后台」）。当时没选「一个后台服务所有项目」，理由是 Runtime 在启动时绑定工作区，要让工作区随会话走需要改配置加载、权限规则与文件索引。

问题报告 U-04（重新进入对话偏慢）实测，用户最大的会话（2.9MB、663 条）切换耗时约 2 秒：

| 步骤 | 耗时 |
|---|---|
| 启动项目后台并握手 | 约 1.0 秒 |
| `listSessions`（172 个会话，整份读日志） | 约 0.15 秒 |
| `resumeSession` | 约 0.95 秒 |
| 订阅与重放 | 约 0.02 秒 |

第一项来自多后台结构：切到另一个项目的会话时，`closeIfIdle` 关掉上一个会话，`releaseIfUnused` 随即结束该项目的后台；切回来再重新起 Node。界面要等全部步骤完成才切换，期间没有任何反馈。

复核 Core 后，ADR-0046 担心的改动大部分已经完成：`wrapSession` 按会话记录的 `meta.workspaceRoot` 加载项目配置、信任状态、权限规则、hooks、MCP、技能与外部 agent；文件索引、输入历史、shell cwd 也按会话取值。仍绑定在后台启动目录上的只有：

1. 项目指令（AGENTS.md 等）在 `createRuntime` 时按启动目录加载一次，所有会话共用（`packages/core/src/index.ts` 的 `instructions`）。在一个后台里恢复别的项目的会话，会拿到错误的指令；这在现有结构下也可能发生（普通对话后台恢复项目会话时）。
2. `createSession` 不能指定工作区，只能用启动目录。
3. 运行时级的设置、服务商、模型查询（`describeSettings`、`describeProviders`、`listModels`、`setDefaultModel` 等）用启动目录的项目层。技能、MCP、外部 agent 的查询已经接受可选 `workspaceRoot`。

## 决定

### 1. 桌面端只有一个后台

- 应用启动时以普通对话工作区为 cwd 启动唯一一个 `nctrn rpc --stdio` 后台，窗口打开期间常驻；所有项目和普通对话的会话都在这个后台里创建和恢复。
- 不再按项目启动或释放后台。会话的空闲关闭（`closeIfIdle`）保留，只关会话，不关后台。
- 之后在设置里更改普通对话工作区，不重启后台：新会话照常按所选目录传 `cwd`。

### 2. Core：工作区随会话

- `CreateSessionOptions` 增加可选 `cwd`（以及与 `createRuntime` 相同语义的可选 `workspaceRoot`），缺省取 Runtime 启动目录，TUI 与 CLI 行为不变。新建会话时按该目录做 `config.forWorkspace`，信任、权限、hooks 等照 `wrapSession` 现有逻辑。
- 项目指令改为按会话的 `workspaceRoot` 与 `cwd` 加载，同一工作区的会话共用缓存；`createRuntime` 传入的 `options.instructions` 仍然优先（测试注入用）。
- 运行时级的设置、服务商、模型查询与写入增加可选 `workspaceRoot`，缺省为启动目录（现有行为）。桌面端在会话上下文里（例如会话的模型菜单）传该会话的工作区；设置页不传，只看用户层与普通对话工作区。
- 实现时逐一核对 Core 中依赖启动目录或 `process.cwd()` 的位置（例如 `platform/process.ts` 在调用方未传 `cwd` 时退回 `process.cwd()`），确认会话内的执行都显式带会话 cwd。Core 不按客户端分支。

### 3. RPC

- `runtime.createSession` 增加可选 `cwd`；第 2 节新增的 `workspaceRoot` 参数照搬到对应方法。均为增量字段，旧客户端不受影响（规则同 [ADR-0044](ADR-0044-rpc-stdio.md)）。
- `runtime.reloadConfig` 保留，供外部改动配置后重载；桌面端不再用它在多个后台之间同步。

### 4. 桌面端

- `BackendPool` 收敛为单个后台的连接管理：握手、退出通知、stderr 读取不变；去掉按 `projectKey` 的多条目、`releaseIfUnused` 和跨后台 `reloadConfig` 协调（含「由我发起」计数）。
- 崩溃恢复沿用 ADR-0046 修订的流程，范围变为全部打开的会话：后台退出时全部标为 `dead`，「重启后台」后逐个 `resumeSession` 并按 `lastSeq` 重新订阅，失败的单独保持 dead。
- 「后台日志」页的后台选择器只剩「后台」与「外壳」两项。
- **切换会话立即生效**：点击会话后先切换选中项并显示「正在打开…」，`resumeSession` 与重放完成后再显示内容；打开失败在该会话内显示错误与重试，不回退到上一个会话。连续快速点击时只保留最后一次的结果。
- **会话列表只读开头**：`store.list()` 只读每个日志文件的开头（足以取到首行与第一条用户消息），读不到第一条用户消息时再读整份；一次切换只刷新一次列表。

### 5. 不变的部分

- TUI、CLI 仍是一个进程一个工作区，行为不变。
- 会话日志格式、会话锁（同一会话同一时刻只有一个进程持锁）不变；其他进程（如 TUI）持锁的会话照旧显示锁并可强制打开。
- 会话树、置顶、普通对话等界面结构不变。

## 后果

- 切换项目不再重启后台；进程数从「项目数 + 1」降为 1；多后台配置同步逻辑删除。
- 后台崩溃会断开所有会话，而不只是一个项目。恢复流程已覆盖，代价是一次重启涉及的会话更多。
- 所有会话共用一个 Node 事件循环。长时间的同步计算（例如大项目首次建文件索引、大会话重建状态）会让其他会话短暂无响应；实现时实测，必要时把这类操作拆成异步分段，不为此恢复多后台。
- `resumeSession` 本身约 1 秒的耗时与本 ADR 无关，另行剖析；本 ADR 只保证界面不再因此卡住。

## 备选方案

- **保留多后台，空闲一段时间后才结束项目后台**：改动最小，但进程数和跨后台同步逻辑都还在，首次进入每个项目仍要等 1 秒。
- **多后台预启动**：启动时为最近的项目预起后台。进程更多，命中率取决于猜测。

## 修订

### 2026-10-07 实现时的补充说明

- **`list()` 头部读取与标题**：`store.list()` 固定只读前 64 KiB（`FileSystem.readFileSlice`）。第 4 节的「第一条用户消息」是 `firstText` 的来源之一；头部窗口内同时记录 `session.titled` 标题，与整份读取的语义一致——但若标题事件写在 64 KiB 之后，头部读取看不到它，`firstText` 会退回第一条用户消息。该取舍接受：日志头部窗口对正常会话足够大，需要完整扫描时（首行截断、头部没有用户消息）仍会回退整份读取。
- **「只保留最后一次的结果」的实现**：打开请求经一条串行队列执行（避免对同一后台并发 `resumeSession`/订阅的竞态），由 `openToken` 标记最新选择；在前的请求晚返回时，若该会话已不在选中位，按空闲路径关闭而不覆盖界面。这满足「界面只采用最后一次点击」，不追求取消在途请求。
- **`workspaceRoot` 键以真实路径为准**：`RuntimeConfig.forWorkspace` 的工作区层按传入字符串缓存；Core 在 `createSession`/恢复时统一写入 `platform.resolveReal` 之后的 `meta.workspaceRoot`，RPC 服务端在派发前也按参数做 `forWorkspace` 预载。客户端应传会话元数据里的 `workspaceRoot`（已解析路径），未解析的短路径会缓存成另一层、查不到项目配置。

### 2026-10-08 RPC 服务端统一解析工作区真实路径

- 第 3 节的运行时级设置、模型、审查器查询与写入，以及带 `workspaceRoot` 的 `provider.*` 方法，统一由 RPC 服务端先经 Core 的 `platform.resolveReal` 解析真实路径，再预加载工作区配置层并转交 Runtime 或配置接口；解析失败时保留原字符串。侧栏目录可能含短路径、大小写差异或符号链接，直接拿原字符串做缓存键会产生重复配置层，因此不再要求客户端必须传已解析路径；2026-10-07 修订中的该客户端要求由本条取代。
