# ADR-0070：运行中插话与排队

- 状态：已接受（被 [ADR-0073](ADR-0073-background-subagents.md) 修订：子代理结果作为待发输入）
- 日期：2026-10-28
- 修订：[agent-loop.md](../architecture/agent-loop.md)、[events.md](../protocols/events.md)、[view.md](../protocols/view.md)、[rpc.md](../protocols/rpc.md)、[context.md](../architecture/context.md)

## 背景

Turn 进行中再次 `submit` 会被拒绝（`session_busy`），用户想纠正方向只能先中断再重发；中断会丢掉进行中的工具调用和已花的时间。[agent-loop.md](../architecture/agent-loop.md) 第 1 节把「运行中追加指令（steering）和输入排队」留作后续设计，[ADR-0052](ADR-0052-remote-web-client.md) 也把「追加消息」列为手机端要完成的事。

## 决定

### 1. 两种方式

- **插话（steer）**：消息并入**当前 Turn**，在下一个安全点交给模型。用于纠偏。
- **排队（queue）**：消息在当前 Turn 以 `done` 结束后，作为**新的 Turn** 发出。用于「做完再做」。

两者统称「待发输入」。会话空闲时提交待发输入，不论哪种方式都立刻作为普通 `submit` 开始新 Turn，避免客户端以为忙、实际已空闲时消息卡住。

### 2. 安全点与插话的消费

插话只在两个位置被消费，都在 Agent Loop 的 Step 之间，不打断模型流，也不打断工具：

1. 一个 Step 的工具调用全部结算后、回到循环顶部构建下一次请求之前。
2. 模型以 `stop` 结束且没有工具调用、本来要以 `done` 结束 Turn 时：有待消费的插话就不结束，写入插话后继续下一个 Step（用户的选择是「等它说完再接」，不打断纯文本输出）。

消费时把当时所有插话按提交顺序**一次性取出**，每条写一个 `message.user`，payload 带 `steer: true`。取出与写入在同一步完成，此后这些条目不能再编辑或撤回。中断信号已触发时不消费。

插话不重新执行 `TurnStart` Hook（Turn 没有重新开始）；`maxSteps` 照常计数，插话导致的额外 Step 也计入。等待权限确认、提问或长时间运行的工具时，插话只能等这一批工具结算，界面需说明「将在当前步骤结束后送达」。

### 3. 排队的消费

Turn 以 `done` 结束后，取队首**一条**排队输入作为新 Turn 的 `submit`；该 Turn 再以 `done` 结束时取下一条。新 Turn 与普通提交完全相同（Hook、附件、`@` 引用、技能）。

错过最后安全点的未暂停插话与排队输入一起按提交顺序开启新 Turn。运行循环完成清理、释放忙状态后立即再检查待发列表，不依赖轮询；空闲时编辑或恢复待发输入也执行同一检查，此时未暂停的插话按排队发送，暂停条目仍须先「继续发送」。

### 4. 非 `done` 结束：暂停

Turn 以 `aborted`、`error`、`truncated`、`refused`、`max_steps` 结束时，剩余的待发输入（包括没来得及消费的插话）全部转为排队并标记**暂停**，不自动发送。用户可逐条编辑、撤回，或「继续发送」恢复自动排队。暂停期间用户直接提交新消息，等同于把新消息追加到队尾并恢复。理由：中断或出错后自动继续发送往往不是用户要的，但消息也不能静默丢掉。

### 5. 编辑与撤回

被消费前，任一客户端都可以修改条目的文本、在插话和排队之间切换、或撤回。编辑只替换用户正文中的文本，保留非文本块；附件、`@` 引用、技能正文与委派指令沿用提交时的快照，要换附件或引用须撤回后重发。条目被消费后修改和撤回返回 `input_consumed`，客户端提示「已经发出，没能撤回」。条目 id 由 Runtime 分配。

### 6. 存放与同步

待发输入是 Runtime 内存中的会话状态，**不写入日志**：它在被消费前不属于对话事实，写进日志会让重放和回退都要处理「提交了又撤回」的历史。每次变化发出临时事件 `input.pending`，内容为完整列表快照，所有订阅者（桌面、手机、TUI）看到同一份；新连接的客户端在附加时拿到当前快照。会话关闭或进程退出时未消费的条目丢失；关闭会话时如有待发输入，客户端提醒。

消费后的插话是持久的 `message.user(steer: true)`，进入历史、重放和导出。

### 7. 历史、上下文与回退

- 插话的 `message.user` 位于工具结果之后。Context Builder 照常按事件顺序构建；工具结果后紧跟用户消息在各 Provider 的格式差异由 Provider 适配器归一化（例如合并进同一条 user 消息），Agent Loop 和 Context 不按 Provider 分支。
- Turn 内压缩覆盖了进行中 Turn 的消息时，按 [context.md](../architecture/context.md) 6.5 节重新注入的内容包括该 Turn 的原始 `message.user` 与其后的全部插话。
- 插话不是回退目标：回退到一条插话会把 Turn 截成半截。回退目标仍是 Turn 起始的用户消息。
- 「任务清单全部完成后由下一条用户消息归档」只由非插话的 `message.user` 触发。
- 子会话不接受待发输入（`invalid_command`）；父会话的插话在父会话的安全点送达。

## 后果

- `message.user` 增加可选 `steer`，属于兼容扩展，不提升 `formatVersion`；旧版本把插话当作普通用户消息显示。
- 新增临时事件 `input.pending` 与 Session/RPC 方法；远程客户端允许调用（属于 ADR-0052 的「追加消息」）。
- 待发输入不跨进程保留。长时间工具执行期间插话可能等很久，由界面说明，不为此打断工具。
- 行模式 CLI 继续在 Turn 期间只接受中断；插话与排队由桌面、手机和 TUI 提供。

## 备选方案

- **立即打断模型流再插话**：丢掉已生成的输出、浪费请求，且用户已选择等它说完；不采用。
- **待发输入写入日志**：恢复后不丢，但撤回、编辑和回退都要进入事件语义，复杂度不成比例；不采用。
- **只在客户端本地排队**：多客户端看不到彼此的队列，手机提交的排队在桌面不可见，也无法在 Turn 结束的同一时刻原子地取出；不采用。
- **非 `done` 结束后继续自动发送**：中断通常意味着用户要重新考虑，自动发送违背意图；不采用。
