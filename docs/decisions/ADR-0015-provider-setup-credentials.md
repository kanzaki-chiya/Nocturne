# ADR-0015：服务商配置向导、机器维护的向导配置层与用户级凭据文件

- 状态：提议
- 日期：2026-09-25

## 背景

v0.1 接入模型服务的方式对新用户不友好：密钥只能放在持久的用户级环境变量里（Windows 上要调用 `SetEnvironmentVariable` 并重开终端），服务商条目要在 `config.json` 里整段手写，服务地址与模型 id 要自己查。目标是提供 `nctrn setup` 与会话内 `/provider` 两个交互入口。

这与两条既有约定冲突：

1. [config.md](../architecture/config.md) 第 1 节："用户配置，程序从不改写它"——向导天然要写配置；
2. 多处文档写明"凭据只经环境变量进入"——引入凭据文件打破这条（[workflow.md](../development/workflow.md) 第 7 节与 [providers.md](../architecture/providers.md) 第 3 节原本已预留"用户级凭据文件"，但从未实现）。

另外，凭据文件第一次让密钥出现在 Agent 工具能触及的文件系统中，而 v0.1 的 `shell` 工具子进程本来就继承含密钥的完整环境。

完整设计见 [provider-setup.md](../architecture/provider-setup.md)。

## 决定

1. **向导写独立的机器维护文件 `<NOCTURNE_HOME>/providers.json`**，作为新的配置层插在"内置默认"与"用户配置"之间。`config.json` 仍然程序从不改写；手写条目按 `id` 覆盖向导条目。
2. **新增用户级凭据文件 `<NOCTURNE_HOME>/credentials.json`**，按服务商 id 存放明文密钥，原子写，POSIX 上 `0600`。解析顺序：条目声明的 `apiKeyEnv` 环境变量 > 凭据文件 > 缺失报错。`apiKeyEnv` 因此变为可选。密钥在每次请求时经注入的 `CredentialSource` 读取，不进入 `ResolvedConfig`、事件或日志。
3. **权限层新增"内置硬拒绝"**：对凭据文件的 `read`/`edit` 在规则求值之前直接 `deny`，任何规则、Grant、`--yes`、`full-access`、Hook 都不能放开。这是 ADR-0004"规则化策略"的第一个非规则化例外，理由是这类访问没有任何合理的放行场景，而放行的代价是密钥外泄。
4. **`shell` 工具子进程剥离凭据环境变量**（全部已解析的 `apiKeyEnv` 名与两个默认名）。Hook 维持继承完整环境（ADR-0012 不变）。
5. **Runtime 新增 `updateProviders`**，运行中替换基础层的服务商配置，会话在下一次空闲边界重建会话级注册表；不采用"关闭并重新打开会话"的做法，以免触发会话生命周期 Hook、重启 MCP 服务器。
6. 向导逻辑（预设、模型列表、连接测试、文件写入）放在 Core 公开 API，CLI 与 TUI 各自实现交互。

## 后果

- 新用户运行一次 `nctrn setup` 即可开始使用；会话内可以随时添加服务商并切换过去。
- 分层多了一层，`/provider` 需要标注每个条目的来源层，避免"改了不生效"的困惑。
- 明文凭据文件的安全性依赖文件系统权限与权限层；一条已获准的 shell 命令仍能读取它（权限不是沙箱）。这一点在 README 与 provider-setup.md 中如实说明。
- 环境变量方式完全保留，已有配置不受影响。

## 备选方案

| 方案 | 结论 | 理由 |
|---|---|---|
| 向导直接改写 `config.json` | 否决 | 丢失用户手写内容的组织方式，混淆"我写的"与"程序写的"；违背 ADR-0007/0008 已确立的"程序写自己的文件" |
| 不存凭据，向导只打印设置环境变量的命令 | 否决（作为向导内的可选路径保留） | 首次配置仍要用户手动执行并重开终端，没有解决核心痛点 |
| 操作系统密钥库 | 推迟 | 需要原生依赖；`CredentialSource` 接口保证以后可替换实现 |
| 凭据写进 `providers.json` | 否决 | 两类数据的敏感度不同，分开存放才能单独施加硬拒绝，也便于只备份或分享配置而不带密钥 |
| 用普通规则保护凭据文件（至少 ask） | 否决 | `--yes` 与 `full-access` 会把它提升为 allow；凭据读取没有需要放行的场景 |
