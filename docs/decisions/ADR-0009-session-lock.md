# ADR-0009：会话锁机制

- 状态：提议
- 日期：2026-09-24

## 背景

[sessions.md](../architecture/sessions.md) 第 4 节要求"打开会话前先取得排他锁，再读取和修改日志"，防止两个进程同时恢复同一会话、交错追加修复事件。需要决定锁的载体、失效判定与逃逸通道。约束：跨平台（Windows 为主开发机）、不引入新依赖、崩溃后不能永久卡死。

## 决定

1. **锁是一个存在性文件** `<sessionId>.lock`，与日志同目录：以"文件不存在才创建"（`wx`）的原子方式创建，内容为 `{ pid, hostname, startedAt }` JSON。持有期间不需要保持打开句柄。
2. **失效判定**：锁已存在时读取内容——
   - `hostname` 与本机不同 → 视为被持有（不支持网络文件系统上的会话目录，文档已声明）；
   - `hostname` 相同且 `process.kill(pid, 0)` 失败（ESRCH）→ 失效锁，删除后重试一次；重试仍撞上锁 → 拒绝打开；
   - 其余（pid 存活、EPERM）→ 拒绝打开，`session_locked`。
   - 锁文件内容损坏且年龄超过短阈值（秒级）→ 按失效处理；新创建的锁内容与读取不符视为竞争失败。
3. **释放**：`close()` 删除锁文件；进程崩溃留下锁文件，由第 2 条的失效判定在下次打开时回收。
4. **逃逸**：CLI 提供 `--force-unlock`（与 `--resume` 搭配）：先删锁再按正常流程取得。这是用户显式声明"持有者已死"的通道，不自动使用。
5. **时机**：`create` 先建锁再写第一行日志；`load` 先取锁再读取——顺序不可调换（sessions.md 第 4 节）。

## 后果

- 实现只需要 `wx` 创建 + `process.kill(pid, 0)` + 文件读写，全部落在 `platform.fs` 的能力范围内，零新依赖。
- **已知限制（如实记录）**：
  - pid 复用会让失效锁看起来"仍被持有"（误判为占用 → 用户用 `--force-unlock`），反向的"活锁被误删"只在 pid 复用且主机相同才可能发生，窗口极小；
  - 存在性锁在 Windows 上可被其他进程删除（不是强制性锁），防的是"Nocturne 进程并发开同一会话"，不防恶意删除；
  - 不覆盖"同一进程内重复打开同一会话"以外的任何并发写日志场景——锁文件之外的写入者仍不受约束。

## 备选方案

- **持有打开句柄 + OS 级文件锁**：Windows 下 Node 不暴露 byte-range lock / 删除共享控制，可移植性差；且句柄方案对"进程被杀"的清理语义与存在性锁相同。
- **proper-lockfile 类库（mtime + 心跳）**：锁活性判定更稳（心跳过期即失效），代价是周期性写文件与一个依赖；在会话锁这种"同机、低频、可人工 `--force-unlock`"的场景收益不成比例。
- **不锁，靠 seq 冲突检测**：两个进程各自持 `nextSeq` 写入会把日志写穿（同 seq 两行），事后无法区分哪条有效——不满足"日志是唯一事实来源"的要求。
