# ADR-0052：远程网页客户端——自建中继、邀请制、端到端加密

- 状态：已接受（第 2 版，2026-10-14）
- 日期：2026-10-08；第 2 版 2026-10-14
- 修订：[ADR-0044](ADR-0044-rpc-stdio.md) 第 2 节「一个服务端进程只有一个 Runtime、一个客户端」与第 8 节「不监听、不鉴权」

> 第 1 版（2026-10-08）的前提是「只有维护者本人使用、局域网或 Tailscale 直连、明文 HTTP」。2026-10-14 维护者确认要给朋友用，前提改变，按本版重写。第 1 版的「同一后台服务多个客户端」保留为第 2 节。

## 背景

长任务交给 Nocturne 跑时，人常常不在电脑前。任务停在权限确认或提问上，要回到电脑前才能继续。需要在手机上查看会话进度，并完成这几件事：批准或拒绝权限确认、回答提问、追加消息、中断。

维护者确认的范围（2026-10-14）：

- **使用者**：维护者和他邀请的朋友。每个人在自己的电脑上装 Nocturne，用手机远程控制**自己的**电脑；没有人使用别人电脑上的 Nocturne。
- **不对所有人开放**：发布版的其他用户没有入口，维护者的服务器只接受受邀的人。
- **借用维护者的服务器**：服务器可以常驻 Node 服务，域名和 HTTPS 证书都有。
- **维护者不接触朋友的内容**：中继只转发，看不到对话、代码、命令和权限请求。
- 做网页，不做原生 App。

现有结构的限制：

- 桌面端只有一个 `nctrn rpc --stdio` 后台（ADR-0051），由 Tauri 外壳逐行转发。
- RPC 服务端一个进程只服务一个客户端（ADR-0044 第 2 节）。会话打开、事件订阅、权限回复都挂在这一个连接上。
- 同一会话跨进程由会话锁互斥（ADR-0009），手机不能另起一个后台打开同一个会话。

## 决定

### 1. 总体结构

```text
手机浏览器 ──WSS──▶ 中继（维护者的服务器） ◀──WSS── 桌面端后台（nctrn rpc）
     └──────────── 端到端加密的 JSON-RPC ────────────┘
```

- **中继**是一个独立的小服务，部署在维护者的服务器上：负责邀请、登记设备、在已配对的手机与电脑之间转发密文、托管手机网页、发送推送。它解不开转发的内容。
- **电脑一侧由桌面端的 Node 后台主动连出**，家里不用开端口，也不用组网工具。后台退出或电脑休眠时离线，手机显示「电脑已离线」。
- **手机一侧**打开中继域名上的网页，经中继与自己的电脑建立端到端加密的通道，通道里跑的就是现有的 JSON-RPC。
- 第一版只做经中继的远程访问。局域网直连以后需要时再加，可以复用第 4 节的加密通道。

### 2. 同一个后台服务多个客户端

- RPC 服务端改为一个 Runtime 服务多个连接：桌面端走 stdio，每台在线的手机各占一个远程连接，共用同一个 Runtime 和同一批已打开的会话。
- **会话按 Runtime 共享，订阅按连接**：
  - 第一个连接 `resumeSession` 时真正打开会话；之后的连接再 `resumeSession` 同一会话，直接返回 `SessionOpened` 和 `lastSeq`，不再报 `session_already_open`；
  - 每个连接各自 `subscribe { afterSeq }`，事件分别推送。手机断线重连后按 `afterSeq` 续接，中继不缓存事件；
  - 会话按引用计数关闭：连接 `close` 或断开只减计数，最后一个连接离开且会话空闲时才真正关闭。运行中的 Turn 不因手机断开而停下。
- **命令谁先到算谁的，Core 不改**：两端同时 `submit`，后到的照常报 `session_busy`；权限确认和提问任一端回复即生效，另一端稍后回复报 `unknown_request`，收到 `permission.resolved` / `question.resolved` 后关闭对应弹窗；`interrupt` 任一端都可以发。
- **Runtime 级通知广播给所有连接**。
- **`interactive`**：只要有一个已连接的客户端声明 `interactive`，就按交互模式处理。桌面端始终声明，实际行为与现在一致。

### 3. 远程连接的能力上限

远程连接意味着能在这台电脑上执行代码，手机丢失或令牌泄露的代价远大于桌面端本机。所以远程连接的能力由**后台**按方法白名单限制，不依赖网页自觉：

- **允许**：列出会话、新建会话（只能在已有项目或普通对话工作区里）、打开与订阅会话、`submit`（只有文字，不带附件）、`interrupt`、`respondPermission`、`respondQuestion`、只读的会话状态查询。
- **不允许**：一切设置与配置写入（包括切换权限预设、模型角色、审查器）、服务商与凭据、登录、MCP 与外部 agent 的增删改和探测、技能导入、回退与分叉、读取附件和任意文件、`reloadConfig`、`shutdown`。白名单外的方法报 `remote_not_allowed`。
- **权限回复的范围**：手机可以批准本次、批准本会话、拒绝；「在此项目中始终允许」「始终允许」这类写入持久授权的选项只能在电脑上选。后台收到远程连接的持久授权回复时按 `remote_not_allowed` 拒绝，请求保持待处理。
- 权限判定仍只在权限层。远程连接只是又一个回复来源，不新增「远程自动批准」之类的规则。
- 方法白名单及精确参数限制以 [RPC 协议第 7 节](../protocols/rpc.md#7-安全与日志) 为唯一主表。
- 桌面端在有远程设备在线时显示标识（例如状态栏「手机在线」），点开可以看到是哪台设备，并能立即断开。

### 4. 端到端加密

目标：中继和服务器上的任何人都看不到内容，也无法伪造或重放命令。

- **身份**：电脑和每台手机各有一对长期密钥（P-256，签名用 ECDSA、协商用 ECDH）。电脑的私钥存进现有的凭据后端（ADR-0015）；手机的私钥是浏览器 IndexedDB 里不可导出的 `CryptoKey`。
- **配对（扫码）**：
  1. 桌面端向中继申请一个配对槽位（随机 id，5 分钟有效，用一次即作废），并在本地生成 32 字节配对密钥 `K`。
  2. 二维码内容为 `https://<中继域名>/#pair=<槽位 id>.<K>.<电脑公钥指纹>`。片段不会发给服务器，所以中继拿不到 `K`。
  3. 手机生成自己的密钥对，经槽位把「手机公钥 + 设备名 + 用 `K` 计算的 HMAC」发给电脑。电脑校验 HMAC 后记下手机公钥，回复「电脑公钥 + 签名 + HMAC」，手机按二维码里的指纹核对电脑公钥。
  4. 电脑通过自己与中继的已认证连接，通知中继允许这台手机（手机 id 和公钥）连到它。
  中继只看到槽位 id 和两边的公钥，没有 `K`，因此无法冒充任何一方完成配对。
- **每次连接的握手**：双方各生成临时 ECDH 密钥，用长期签名密钥对「双方临时公钥 + 双方身份 + 协议版本」签名并互相校验，再用 HKDF-SHA256 从临时 ECDH 结果派生两个方向各自的 AES-256-GCM 密钥。这样有前向保密：长期密钥将来泄露，也解不开以前录下的流量。
- **报文**：每条 JSON-RPC 报文单独加密，nonce 用按方向递增的计数器，收到的计数器不递增就断开，以此防重放和乱序。
- **只用 WebCrypto**：Node 24 和现代浏览器都有同样的 `crypto.subtle`，加密模块一份代码两端共用，不引入第三方密码库。握手细节在第 2 轮单独评审，并附测试向量和篡改、重放、错配密钥的测试。

**绕不开的信任点**：手机网页由中继下发。如果服务器被人改了网页代码，页面可以在解密前拿走手机私钥的使用权，端到端加密防不住这一点。要堵住它，只能做原生 App 或浏览器扩展，小圈子使用不值得。所以实际的信任边界是：**朋友信任维护者和他的服务器不会被篡改网页**；中继进程本身即使被入侵，只要网页没被改，也看不到内容、伪造不了命令。这一点在远程设置页和部署文档里写明。

### 5. 中继服务

- **形态**：新增 `apps/relay`，一个 Node 服务，监听本机端口，放在维护者已有的反向代理（nginx、Caddy 等）后面，由反向代理提供域名和 HTTPS。随 Release 附 `nocturne-relay-<version>.tgz` 和部署说明，朋友不需要接触它。
- **不开放注册，邀请制**：
  - 中继的管理员（维护者，或自建中继的人）在服务器上用命令行管理：`nocturne-relay invite create [--note 名字] [--expires 7d]` 生成一次性邀请码；`host list`、`host revoke <id>`、`device list`、`device revoke <id>`。第一版不做管理网页。
  - **邀请码自带中继地址**：`invite create` 输出一串邀请，形如 `nocturne-invite:<中继域名>/<邀请码>`。朋友在桌面端粘贴这一串即可，不用另填地址；电脑生成长期密钥，用邀请码向中继登记公钥，邀请码随即作废。
- **两种用法，同一套代码**：
  - **使用别人的中继**：拿到中继管理员（例如维护者）给的邀请，粘贴登记。
  - **自建中继**：在自己的服务器上按部署文档装好中继，自己生成一份邀请给自己的电脑，也可以发给自己的朋友。

  两种用法在桌面端没有区别，都是粘贴邀请；区别只在中继由谁运行。发布版里**不内置任何中继地址**，包括维护者的：避免把维护者的域名写进公开仓库、变成事实上的公共服务。
- **自建门槛**：中继随 Release 提供 tgz 和 Docker 镜像，配置只有监听端口、数据文件路径、对外域名、VAPID 密钥（首次启动自动生成）和限额；HTTPS 交给已有的反向代理。部署文档给出 Caddy 与 nginx 示例。
  - 吊销电脑或手机后，中继立即断开对应连接并拒绝重连。
- **连接认证**：电脑和手机连上中继后，用各自的长期私钥对中继下发的随机挑战签名。中继只允许已配对的手机与对应的电脑互通，其他组合一律拒绝。
- **只转发**：中继按「手机 id → 电脑 id」转发密文帧，不解析、不缓存、不记录内容。日志只有连接、认证结果、字节数与时间。
- **限额**：每台电脑最多 5 台手机；单帧上限 1 MB；邀请码、配对、认证失败按来源限流（例如每分钟 10 次）；每台电脑的并发连接数有上限。限额可在中继配置里调。
- **存储**：一个 JSON 文件（原子写），记录邀请码哈希、电脑与手机的 id、公钥、备注、创建与最近在线时间、吊销状态。不需要数据库。
- **托管网页**：同一个域名下提供手机网页的静态文件，版本随中继发布。

### 6. 推送通知

- 网页是 HTTPS，可以装成 PWA 并订阅 Web Push。
- 电脑在需要提醒时（规则与 ADR-0056 相同：需要确认、出错停止、长任务完成，且手机端没在看）通过中继触发推送。
- **第一版推送内容是通用文字**（例如「Nocturne：有会话需要你处理」），不带会话标题或任何内容，中继和推送服务商都看不到细节。点开后网页连上电脑再显示具体内容。
- VAPID 签名由中继完成，用 Node 内置 `crypto` 实现，不引入推送库。以后如果要带会话标题，可以由电脑按 RFC 8291 把载荷加密给手机的订阅，中继只转发密文，另行决定。

### 7. 桌面端

- **「设置 › 远程」**：粘贴邀请登记（登记后显示所连中继的域名，可以退出登记、换一个中继）、连接状态、「允许远程访问」总开关、「配对新手机」（显示二维码）、已配对手机列表与吊销、信任边界说明。没有登记时只显示一段说明（怎么向别人要邀请、怎么自建中继），没有任何联网行为。
- 中继登记信息、开关和设备列表存在用户级配置里，项目层不能覆盖（避免不受信任的仓库把电脑接到别人的中继上）。
- 状态栏的远程标识见第 3 节。
- 只有桌面端的后台提供远程访问。TUI 的 Runtime 在进程内，不经 RPC 服务端，第一版不支持。

### 8. 手机网页

- 复用桌面端前端：在 `apps/desktop` 新增网页入口，用 `WebHost` 实现 `DesktopHost` 接口，传输层是第 4 节的加密通道加 WebSocket。打开文件、在资源管理器中显示、更新等宿主能力在网页里不可用。网页入口不得引入 Tauri API。
- **第一版功能**：会话列表、打开会话、看消息流和工具调用（折叠显示）、发送文字消息、中断、回复权限确认与提问（底部弹出面板）、在已有工作区里新建会话、多台电脑之间切换（同一台手机可以配对自己的多台电脑）。
- **第一版不做**：设置页、服务商与 MCP 管理、附件、回退与分叉、技能导入、文件打开。
- 布局按手机竖屏设计：单栏，会话列表和会话页之间导航切换。
- **入口与密钥保存**：配对链接一次性、5 分钟有效；配对完成后网页把地址栏换成不带片段的 `https://<中继域名>/`，以后从书签或主屏幕图标打开这个地址即可。这个地址本身不含任何凭据，没配对过的浏览器打开只能看到配对说明。手机私钥只在这个浏览器里：清除网站数据或换浏览器就要重新配对。iOS Safari 会清理 7 天没访问的普通网站数据，配对完成后网页提示「添加到主屏幕」，装成 PWA 后不受这条限制。
- **版本兼容**：网页随中继发布，电脑随桌面端自动更新，两边版本可能不同。握手时比较 RPC `protocolVersion`，不兼容时网页提示「请更新桌面端」或「中继版本过旧」，不尝试降级运行。维护者每次发版同步更新中继。

### 9. 模块与依赖

- `packages/remote`（新）：加密通道、配对与握手、帧格式。只用 WebCrypto 和标准 Web API，不依赖 Node 内置模块与 Core，电脑后台和手机网页共用。
- `packages/rpc`：多连接、远程连接的方法白名单、电脑一侧连接中继的客户端（Node 24 内置 `WebSocket`）。
- `apps/relay`（新）：中继服务。只依赖 `packages/remote` 的帧类型，不依赖 Core 与 rpc。
- `apps/desktop`：远程设置页、二维码、网页入口。
- 依赖方向写进 modules.md 与 `.dependency-cruiser.cjs`。
- **需要的第三方包**（引入前经维护者同意）：中继的 WebSocket 服务端（例如 `ws`）；生成二维码的库。加密与推送不引入第三方包。

### 10. 不变的部分

- Core 不改：多客户端、白名单和远程连接都在 `packages/rpc` 与新包里实现。
- 会话日志、会话锁、权限层、事件协议不改。
- 没有登记中继时，后台与今天完全一样，不发起任何网络连接。

## 后果

- 发布版不内置中继，其他用户没有邀请就用不了远程功能，也看不到维护者的域名。想用的人可以按文档自建中继，给自己和朋友用，与维护者的服务器互不相干。
- 远程访问相当于在手机上远程执行代码。安全边界是：邀请制、配对密钥不经过中继、端到端加密与双向认证、后台方法白名单、持久授权只能在电脑上做、设备可随时吊销。
- 实际信任边界包含「中继下发的网页没有被篡改」，需要对朋友说清楚。
- 维护者要运维中继：随版本更新、管理邀请与吊销、承担带宽。中继不存内容，泄露的只有设备登记信息。
- RPC 服务端从单连接变为多连接共享 Runtime，会话引用计数、断线清理、通知广播、各连接的 `afterSeq` 续接都要重新测试。
- 网页与桌面共用前端，桌面界面的改动会影响网页端，需要在测试中覆盖网页入口。

## 备选方案

- **局域网或 Tailscale 直连**（第 1 版）：只适合维护者本人；让朋友加入维护者的 tailnet 门槛高，也等于把他们的设备拉进维护者的内网。否决；以后可以作为补充模式。
- **发布版内置维护者的中继作为默认选项**：朋友少填一步，但维护者的域名会写进公开仓库，所有用户都看得到这个入口，容易被当成公共服务来用或来试探。邀请里已经带了地址，内置没有必要。否决。
- **中继能看到明文**（只靠 HTTPS 到中继）：实现简单，但服务器一旦被入侵，所有朋友的电脑都会暴露，维护者也能看到朋友的内容。否决。
- **原生 App**：能消除「网页被篡改」这个信任点，推送也更好，但要适配 iOS 和 Android、签名与上架，小圈子使用不值得。以后需要时可以用同一套前端套壳。
- **账号体系与第三方登录**：邀请码加设备密钥已经够用，账号体系增加运维和泄露面。否决。
- **由 Tauri 外壳连中继并多路复用**：要在 Rust 里重写 JSON-RPC 多路复用和会话去重。否决。
- **Bot 通道（微信、Telegram）**：内容会经过第三方平台，与端到端加密的目标冲突。否决。

## 实现计划（建议分轮）

1. **RPC 多连接与白名单**：多个连接共享 Runtime、会话引用计数、通知广播、远程连接方法白名单、持久授权拒绝。只用内存传输测试，不涉及网络。
2. **加密通道**：`packages/remote` 的配对、握手、帧加密；测试向量与篡改、重放、错配密钥测试。握手设计在本轮开始前单独评审。
3. **中继服务**：`apps/relay` 的邀请、登记、挑战认证、转发、限额、管理命令、静态托管、推送；进程内 WebSocket 测试。
4. **桌面端**：后台连中继、「设置 › 远程」、二维码、设备管理、状态栏标识。
5. **手机网页**：`WebHost`、加密传输、单栏布局、底部权限面板、PWA 与推送；真机验收。

每轮完成后都可以独立验收；第 1 轮也为将来的 IDE 插件等多客户端场景打基础。

## 修订

### 2026-10-14：Runtime 由本机连接创建

第 2 节「只要有一个已连接的客户端声明 `interactive`，就按交互模式处理」改为：Runtime 只由本机连接（桌面端的 stdio）在握手时创建，`interactive` 取自本机连接的声明；远程连接不创建 Runtime，本机连接尚未握手完成时远程握手报 `runtime_unavailable`。原因是 Runtime 的 `interactive` 在创建时固定，按连接动态切换要改 Core，而桌面端始终声明交互，结果相同。本机连接断开即整个后台收尾，远程连接随之关闭；远程连接断开只清理它自己，不中断运行中的 Turn。

### 第 1 轮实现核对：提问结算事件

第 2 节的 `question.resolved` 是设计文字误记，既有 Core 没有该事件；本轮保持 Core 不变，提问回复后沿用 `runtime.status(running_tool)` 与对应 `tool.completed` 收束，重复回复仍报 `unknown_request`。权限回复仍广播已有的 `permission.resolved`。精确契约见 [RPC 协议](../protocols/rpc.md)。

### 2026-10-14：第 2 轮握手定稿

- 长期密钥只用 ECDSA，ECDH 只用临时密钥：同一 WebCrypto CryptoKey 不能兼任两种算法，手机私钥不可导出也无法转换用途。
- 握手、配对的精确定义以 [remote-channel.md](../protocols/remote-channel.md) 为准。
- 配对报文里的设备名对中继可见；中继本来就要在 `device list` 里显示它。

### 2026-10-14：第 3 轮中继协议定稿

- 推送无载荷，由 service worker 显示固定文案。
- 管理命令走本地管理通道，不直接写数据文件。
- 精确协议见 [relay.md](../protocols/relay.md)；中继客户端位于同构 `packages/remote`，服务运行时只依赖 remote 与 ws。
- 维护者澄清：device.remove/unregister 保留管理员吊销墓碑，防止同一公钥重新登记绕过吊销。
