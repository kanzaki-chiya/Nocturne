# ADR-0029：TUI 深浅主题与配色切换

- 状态：已接受（维护者 2026-09-30 确认）
- 日期：2026-09-29

## 背景

[v0.5 路线图](../roadmap/roadmap.md)要求先统一配色，再做依赖配色的界面打磨。当前 TUI 虽把一部分颜色集中在 `theme.ts`，仍以单套命名色为主，状态栏各段使用不同亮色，diff 等区域也有独立底色。浅色终端上的可读性和整体层级无法仅靠替换一个 `accent` 保证。[ADR-0019](ADR-0019-tui-visual-provider-page.md)确定的语义色集中管理原则继续有效；本 ADR 具体规定可切换主题、预览及持久化行为，并取代其“状态栏分段彩色”的配色决定，不改变布局和数据流。

## 决定

### 1. 范围与配色

首版只提供内置 `dark`、`light` 两套 TUI 主题，分别适配深色、浅色终端背景；用户按自己的终端底色选择，从未选择过时默认为 `dark`。每套使用明确的颜色值，而非依赖终端的 `cyan`、`gray` 等命名色：一个主色、两到三档中性色，以及低饱和的成功、警告、错误色。正文、弱化文本、选中态、选区、边框及局部区块底色按语义角色取色；选区不再依赖终端反色，Todo 固定区边框使用边框角色。主题角色及两套调色板集中在 TUI 的主题模块；现有组件中的硬编码颜色迁入相应角色。保留现有 Todo 清单和其他界面的结构、状态符号与交互，只调整颜色和必要的对比度。Todo 的 ✅🟦⬜ 是由字体决定颜色的 emoji，两种终端背景下都要可读，实现时不额外给它们上色。

状态栏以中性色为主，最多突出一到两个重要信息；警告或错误仍可用语义状态色。Markdown 标题、代码和引用主要靠灰度、粗细及排版区分，不用彩虹色区分类型。实现阶段用仅供开发的预览方式展示几组临时候选主色，分别附 Windows Terminal 深色、浅色配色方案下的截图，交维护者挑选。确定后删掉临时候选，只发布 `dark`、`light` 两套最终色值；运行时 `/theme` 不提供主色挑选。精确色值只保证支持真彩色的终端，以 Windows Terminal 为验收目标；其他终端由 chalk 自动降级至最接近的颜色，降级后的色彩效果不在验收范围内。

### 2. `/theme` 预览与应用

TUI 输入 `/theme` 打开仅含 `dark`、`light` 的主题选择页。上下键移动高亮项时，页面下方立即以候选主题绘制示例，涵盖用户输入、含标题/代码/列表的回答、工具行、diff、权限提示和状态栏；示例区显式使用深色、浅色底色并排展示候选主色，宽度不足时改为上下排列。示例使用与实际界面相同的主题角色和渲染路径，避免预览与应用结果不同。

`Enter` 保存所选主题，保存成功后立即应用于当前 TUI；`Esc` 关闭页面并恢复进入前的主题，不写设置。预览只影响选择页，不改变对话历史或其他正在显示的界面。保存失败时留在选择页、提示错误，当前主题和持久设置均不改变。帮助和补全只在可使用该命令的 TUI 中宣传它；逐行 CLI 不提供一个无法执行的 `/theme` 命令。

### 3. 设置归属与渲染边界

选择以 `theme: "dark" | "light"` 存入机器维护的 `<NOCTURNE_HOME>/settings.json`，下次启动及恢复会话时沿用。Core 现有的 `setShellSetting` 只处理 shell，故在公开的 `RuntimeConfig` 上新增可复用的字符串偏好接口：`getPreference(key: string): string | undefined` 和 `setPreference(key: string, value: string | undefined): Promise<void>`；`undefined` 表示删除该字段。接口读写 `settings.json` 顶层的普通字符串偏好字段，`shell`、`shellPath` 等有专用语义的字段仍走原有接口，通用写入端拒绝这些保留字段。Core 原子写盘成功后才更新内存值，并保留未知字段；手写 `config.json` 始终不改写。未来 `/settings` 页可复用此入口，不需另造 `setTheme`。

TUI 只有公开的 `Runtime` 和 session，不直接持有 `RuntimeConfig`。因此在 `Runtime` 上也公开同签名的 `getPreference`、`setPreference`，内部转交给注入的 `RuntimeConfig`。`createRuntime` 未传入 `config` 时，`runtime.getPreference(key)` 返回 `undefined`；`runtime.setPreference(key, value)` 返回被拒绝的 Promise，错误明确指出未注入 `RuntimeConfig`、无法保存偏好。TUI 保存主题遇到此错误时，按第 2 节留在选择页并提示，当前主题不变。Core 只把 `theme` 当普通字符串存取，不认识 `dark`/`light`，也不依赖调色板、Ink 或终端能力；TUI 自行判断取值是否合法，缺失或无效时回退深色。设置文件损坏沿用现有警告路径，不阻塞启动。主题是用户界面偏好，不进入会话事件、`SessionState`、`SessionView`、模型上下文或 `formatVersion`，不按会话分别保存。实现时把 `RuntimeConfig` 与 `Runtime` 的偏好接口契约写入[配置设计](../architecture/config.md)；若 `Runtime` 公开方法另有主文档，也在那里补一句并链接到配置设计。

`dark`、`light` 是适配终端原有深浅背景的两套前景配色；全屏和普通屏幕 `--inline` 都遵守同一规则。TUI 不涂满整屏，保留终端自己的背景、透明效果和背景图。只有 diff 行、代码块、浮层与对话框、`/theme` 示例区等局部区块显式指定底色，并按各主题保证文字可读。用户应选择与终端底色相配的主题；程序不自动探测或更改终端背景。不得修改 Windows Terminal 配置或持久终端调色板。普通屏幕 `--inline` 中已经写入滚动历史的内容无法重着色；切换后新输出使用新主题，已输出内容原样保留。退出时不遗留临时终端颜色状态。`NO_COLOR`、`TERM=dumb` 时不输出配色控制序列；ASCII 和窄终端下，文字、标记、边框和键盘操作仍能表达状态，不依赖颜色单独传意。

运行中的主题由 React context 提供给 TUI 组件，不再由模块加载时固定的常量决定。全屏 `lines.ts` 的 block 排版缓存 `revision` key 包含主题 ID，主题切换后已排好的行也必须按新颜色重新排版。TUI 在第一次渲染前读取已保存的主题，避免启动时先闪默认色再切换。

## 验收

- `dark` 在 Windows Terminal 深色配色方案下、`light` 在浅色配色方案下目视核对，包括选择页示例、全屏主界面、Todo、权限提示及窄终端；diff、代码块和浮层的局部底色在两种终端背景下都清晰可读。两套最终色值已由维护者确认。
- 验证 `/theme` 的上下预览、`Enter` 保存、`Esc` 取消和写入失败回退；重启、恢复会话后选择仍生效，未设置或无效值默认深色。
- 在隔离的 `NOCTURNE_HOME` 验证 `settings.json` 原子更新且保留 `shell`、`shellPath` 和未知字段；手写 `config.json`、会话日志不变。
- 检查全屏与 `--inline` 实际渲染、运行中切换后缓存重排、启动无默认色闪烁、窄宽度、`NO_COLOR`、ASCII，以及 CLI 帮助/补全不误报命令；自动测试离线运行，不依赖真实服务。
- 实现时同步[配置](../architecture/config.md)、[TUI](../apps/tui.md)及相关用户文档；在配置设计中记录 `RuntimeConfig` 与 `Runtime` 的偏好接口契约，若 `Runtime` 公开方法另有主文档，也补一句并链接。

## 后果

深浅界面由同一组语义角色控制，后续页面可沿用既有角色。代价是现有零散色值需要一次性梳理，并为局部底色、选区和缓存重排逐一核对。主题属于跨会话设置；已打印的普通屏幕历史保留原色，这是终端输出的固有限制。

## 备选方案

未采用由 TUI 涂满整屏背景：`--inline` 的滚动历史无法补底色；每个格子补齐底色还会牵涉选区反色、emoji 双宽和空行占位等渲染路径，并覆盖用户终端的亚克力效果与背景图。同类产品 Claude Code、omp 也采用适配终端背景的深浅前景方案。未采用直接切换终端的全局背景或 Windows Terminal 配置：会影响其他程序且难以安全恢复。未首版开放任意自定义色值、导入主题或第三方主题包：两套内置主题足以验证配色与切换机制，扩展时再定义兼容契约。未在 CLI 复用 TUI 主题：逐行 CLI 的颜色行为与页面式预览不同，本次目标仅是 TUI。未将主题写入手写 `config.json` 或会话日志：这既不属于会话事实，也不应由程序改写用户配置。
