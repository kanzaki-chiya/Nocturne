# ADR-0082：电脑操控

- 状态：已接受
- 日期：2026-11-07
- 修订：[permissions.md](../architecture/permissions.md)、[mcp.md](../architecture/mcp.md)、[desktop-browser.md](../protocols/desktop-browser.md)（运行时来源）、[desktop.md](../apps/desktop.md)、[workflow.md](../development/workflow.md) 第 8 节

## 背景

用户想让模型直接操作没有命令行或 API 的 Windows 软件。现在的做法是自己装 cua-driver（[trycua/cua](https://github.com/trycua/cua)，`libs/cua-driver`，MIT），在 `mcp.json` 里登记它。这能用，但要用户自己装、自己配，权限也只能按工具放行（`mcp cua-driver/click`），不知道点的是哪个软件。

调研报告（`nocturne-mockups/research/cua-driver.md`，cua 提交 `895aec7e`）的结论：cua-driver 已经做好 Windows 的控件树读取、截图、后台和前台输入、结果核对，以及多种界面框架的端到端测试；自己重写要三到六人月，把它的库嵌进进程又带来原生模块、DPI 和升级维护的问题。缺的是宿主这一侧：按软件授权、不确定结果时停下、让用户看到它在做什么。

## 决定

### 1. 分发

- 桌面端 Windows 安装包内置 cua-driver 官方发布的可执行文件（`cua-driver.exe` 及其随附程序），放在 Tauri resources 的 `cua-driver/` 下。用官方签名的发布包，不自己编译；版本锁定，`release-build` 下载后按记录的 SHA-256 校验，不符即构建失败。版本号和哈希记在仓库里一处，升级只改这一处。
- 只打包 `cua-driver` 本体。不打包 `cua-driver-bench`、Spaces（FSL-1.1-MIT）和 `cua-perception` 视觉扩展（含 AGPL-3.0 组件）。
- `THIRD-PARTY-NOTICES.md` 收录 cua 的 MIT 许可全文和它发布包里随附的第三方声明。
- CLI/TUI 的 npm 包不带驱动，自行启动的后台没有电脑操控。其他平台以后再议。

### 2. 接入

- 走 `packages/mcp` 已有的运行时服务器来源（与 [desktop-browser.md](../protocols/desktop-browser.md) 第 1 节同一机制），服务器 id 为 `computer`，模型看到的工具名是 `mcp__computer__<tool>`。不写 `mcp.json`，不新增 Core 工具，Agent Loop 不按工具名分支。
- 外壳在 spawn 后台时通过进程专属环境变量交出驱动路径；后台入口在加载配置前读出并删除该变量。没有该变量就完全不装配。
- 传输是 stdio：`cua-driver mcp`。**整个后台只起一个驱动进程**，所有会话共用；焦点和剪贴板是全机唯一的，多个驱动进程会互相打架。
- 启动驱动时：关闭遥测与启动更新检查（cua 默认开启并上报 PostHog）；驱动自己的目录变量（`CUA_DRIVER_RS_HOME`、`CUA_DRIVER_HOME`、`CUA_DRIVER_LOCAL_HOME`、`CUA_DRIVER_CURSOR_THEME_DIR`、`CUA_DRIVER_TELEMETRY_HOME`、`CUA_HOME`）都指向 Nocturne 用户数据目录，不修改 `HOME`、`USERPROFILE`、`LOCALAPPDATA`、`APPDATA`，被驱动通过 `launch_app` 启动的软件使用用户本来的环境。`cua-driver` 启动时仍按只读方式尝试读取 `~/.cua-driver/config.json`，但在 `mcp --direct` 与白名单工具下不会向用户目录写入文件。具体环境变量名以锁定版本的源码为准。
- 用户另外在 `mcp.json` 登记的 cua-driver 照常工作，与内置来源互不相干。

### 3. 工具范围

- 按白名单暴露：应用和窗口列举、窗口状态与截图、整个桌面状态、`verify_state`、启动/调整窗口、点击/拖拽/滚动、输入与按键、剪贴板读写、光标控制。
- 不暴露：`browser_*`（Nocturne 已有 Agent 浏览器）、`check_for_update`、扩展安装与视觉扩展、录制与回放（`replay_trajectory` 会真的重新执行动作）。
- 白名单写在来源里，按锁定版本 `tools/list` 的实际名字维护；驱动升级多出来的工具默认不暴露。

### 4. 权限

- 新增权限类别 `app`。授权键是**应用身份**：普通程序取 exe 文件名的小写形式；打包应用（UWP / MSIX）取包族名，不能按 `ApplicationFrameHost.exe` 授权。显示名和图标只用于界面，不参与匹配。
- 带目标窗口或进程的工具（点击、输入、按键、窗口状态、启动应用等）声明 `app` 主体。工具入参只有 PID 或窗口句柄时，由执行器在解析阶段把它解析成应用身份，和路径主体的解析同一层次；解析失败按 `ask` 处理并在确认卡里显示原始 PID。权限判定仍只在权限层。
- 不带目标的工具（列举、整个桌面状态、剪贴板、光标）在总开关打开后不产生 `app` 主体，也不询问。
- `app` 不受权限预设影响，所有预设下默认都是 `ask`，与 `subagent external:*` 相同。
- 规则存在用户层：设置页「权限」里的「其他软件」是 `app *` 的动作（允许 / 询问 / 拒绝，默认询问），逐个软件的条目是精确规则。项目配置不能放宽 `app`。
- 确认卡选项只有三项：「本会话允许」（会话 Grant）、「始终允许 <软件名>」、「拒绝」。「始终允许」新增 `PermissionOption` 值 `allow_always`，由权限层写一条用户层 `app <身份> → allow` 规则，设置页随即出现该软件；只在所有主体都是 `app` 时提供。写入失败降级为会话 Grant 并发 `runtime.warning`，与项目 Grant 一致。
- 允许过的软件，在其中点击、输入、截图、切到前台都不再询问。

### 5. 不询问的动作与补偿

- **切到前台**：不询问。驱动用前台方式送达期间，桌面端状态栏显示正在操作的软件，并带停止按钮；全局快捷键 `Ctrl+Alt+Esc` 中断当前 Turn（注册失败时状态栏显示快捷键不可用）。
- **写剪贴板**：不询问。一个 Turn 里第一次写剪贴板前，来源先读出当前的文本内容保存；Turn 结束时，如果剪贴板还是我们写进去的内容，就恢复原内容；用户中途自己复制过就不动。非文本内容无法保存时照常写入，不阻止。
- **截取整个桌面**：不询问，截图照常显示在对话里。
- **结果不确定**：驱动返回无法核对、未知或令牌失效时，不自动重试，也不自动换成前台方式重发；工具结果原样交给模型，由模型重新观察。这条写进来源给模型的工具说明，不在 Agent Loop 里实现。
- 发送、删除、付款这类不可逆的业务操作，驱动分辨不出来，不在本层确认；靠模型在执行前用 `ask_user` 问用户。

### 6. 界面

- 设置新增「电脑操控」页，在「浏览器」之后，效果图见 Artifact HJiqxHS4BZvLZbCU1m69Lq：
  - 「电脑操控」总开关，默认关。打开时先出现一行确认：「模型能看到你的屏幕，并在允许的软件里替你点击和输入。」与「取消 / 仍然启用」。关掉后本页其他项变灰，驱动停止，工具消失。
  - 「驱动」行：状态点（运行中 / 启动中 / 未启动 / 出错）、`cua-driver <版本>`、「重启」按钮。
  - 「显示光标」开关，控制驱动的模型光标。
  - 「权限」组：「其他软件」下拉，逐个软件的条目（图标、名称、exe 名、下拉、移除），「+ 添加软件」从正在运行的软件里选，最后一项「浏览…」选 exe 文件。
- 确认卡复用现有权限确认卡，效果图见 Artifact A1mzNRzwWLYsAzSy8iFD3J：主体一行显示软件图标、名称、exe 名和窗口标题；按钮为第 4 节的三项，按 1–3 选择，Esc 拒绝。
- 开关和光标设置存桌面本机 prefs；开关改动当场生效（启停驱动并在下一个 Turn 边界更新工具集），不要求重启应用。
- 不新增本节以外的界面文字、说明或提示。

## 不做

- 自研驱动、把驱动库嵌进进程。
- 在驱动层识别不可逆操作并确认。
- 后台不抢焦点的全局承诺：驱动的后台送达仍有已知问题（cua issue #4843、#5711），只当作加分项。
- 手机和安卓端的电脑操控设置；手机发起的 Turn 若用到这些工具，确认卡按现有权限确认卡显示。
- CLI/TUI 独立后台的电脑操控。

## 后果

- 用户不用自己装驱动；权限按软件而不是按工具，同一软件只问一次。
- 安装包增加约 50MB，每次自动更新都要下载。
- 驱动升级跟着 Nocturne 发版走，要重新跑白名单和权限测试。
- 杀毒软件可能拦注入输入的程序；用官方签名降低风险，但不能排除。
- 驱动卡死或崩溃只影响 `computer` 来源，按 MCP 现有的崩溃与重连处理。

## 备选方案

- **继续让用户自己装、在 `mcp.json` 里登记**：零改动，但权限只能按工具放行，体验靠用户自己配。
- **把驱动的库作为依赖嵌进进程**：能直接对接权限，但要处理原生模块、DPI 感知与宿主冲突、体积和跟进上游的维护成本，消除不了驱动本身的问题。
- **参考它自研 Windows 层**：完全可控，但仅前台可用版就要六到十人周，跨框架稳定要三到六人月。
