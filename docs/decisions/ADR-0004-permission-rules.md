# ADR-0004：规则化的权限策略层

- 状态：已接受（第 2 版，2026-09-23）
- 日期：2026-09-23

## 背景

Coding Agent 会读写文件、执行命令，必须在执行前按用户意愿判定 allow / ask / deny。参考项目：

- **ZCode**：`PermissionService.checkPermission` 是一条很长的判定链，按模式（build / edit / plan / yolo / auto）分支，并包含若干按工具名的特判与按名字维护的工具集合；`yolo` 在注释中被承认先于"禁用工具"放行。审批请求通过 `PermissionBrokerPort` 与判定逻辑分离，这一点设计良好。路径层当前不阻止访问工作区外的路径。
- **OpenCode**：规则是 `(permission, pattern, action)` 的扁平列表，按"最后一条匹配"求值，未匹配时为 ask。
- **Codex**：审批策略（何时询问）与沙箱策略（操作系统层面允许什么）是两个正交维度。

第 1 版的问题（评审指出）：让不可信的项目配置参与"最后一条匹配"的覆盖，只忽略其 allow，仍会出现"用户 deny、项目 ask → 最终 ask"，即项目配置放宽了用户的限制。

## 决定

1. 权限是独立模块，只对解析后的主体做纯策略判断。需要 I/O 的资源解析（真实路径、符号链接、junction）由 Tool Executor 通过 `platform` 完成。
2. **规则排序与信任边界分开定义**：
   - 可信规则（内置预设 < 用户配置 < 可信项目配置 < 命令行参数）内部按"最后一条匹配"求值，未匹配为 ask。
   - 不可信的项目规则不参与排序，只与可信结果**取更严格者**；其中的 allow 被忽略。它只能收紧，永远不能放宽。
3. **Grant**（"本会话内允许"、"在此项目中始终允许"）只能把最终的 `ask` 变为 `allow`，永远不能改变 `deny`。项目级 Grant 存放在用户数据目录，不写入仓库。
4. 预设只是规则集合，没有代码分支。
5. shell 命令含控制符时，模式 allow 不适用，Grant 只能精确匹配。
6. 枚举类工具不跟随符号链接，并按规则逐条过滤结果。
7. ask 通过事件请求与命令回复完成（见 [ADR-0002](ADR-0002-ui-independent-core.md)）；无人回复时默认 deny。
8. 明确声明权限层不是沙箱。

详细规则见 [permissions.md](../architecture/permissions.md)。

## 后果

- 判定逻辑小而可测；"不可信来源只能收紧"成为算法本身的性质，而不是依赖若干特例。
- 新工具只需声明主体，无需修改权限代码。
- 路径判定与执行之间存在竞争窗口，只能通过写入前复核缩小；shell 基于字符串模式匹配，危险命令识别只是提示。这些限制需在文档与界面中如实说明。

## 备选方案

- **模式驱动的判定链**（ZCode）：初期直观，但每种模式都在代码里分支，随功能增长而膨胀。
- **所有层统一"最后一条匹配"**（第 1 版）：简单，但无法保证不可信来源只能收紧。
- **由工具在执行中自行请求权限**（OpenCode 的工具通过 `ctx.ask` 发起）：工具可以精确表达需求，但判定分散在各工具中，不易审计，也可能被遗漏。
- **首版即实现操作系统沙箱**：安全性最好，但跨平台实现成本高，超出 MVP 范围。
