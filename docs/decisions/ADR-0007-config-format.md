# ADR-0007：配置文件格式与分层

- 状态：已接受
- 日期：2026-09-24

## 背景

Phase 3 引入 `config` 模块（分层配置）。需要决定：配置文件放在哪里、用什么格式、各来源如何排序、凭据如何进入。约束：

- CLI 的运行时第三方依赖为零（[apps/cli.md](../apps/cli.md) 第 9 节）；Core 已有 Zod 做运行时校验。
- 配置是面向用户手写的文件，注释可读性有价值。
- 凭据不得写入任何配置文件或会话日志（[workflow.md](../development/workflow.md) 第 7 节）。

## 决定

1. **位置**：用户配置 `<NOCTURNE_HOME>/config.json`；项目配置 `<workspaceRoot>/.nocturne/config.json`。仓库内只出现 `.nocturne/` 一个目录（repository-layout.md 第 5 节已有约定），会话数据与授权记录都留在 `NOCTURNE_HOME`。
2. **格式**：严格 JSON + Zod 校验。不支持注释与尾逗号。
3. **分层**：内置默认 < 用户配置 < 项目配置 < 环境变量 < 命令行参数；合并规则与逐字段语义见 [config.md](../architecture/config.md)。
4. **凭据**：配置文件中只允许 `apiKeyEnv`（环境变量名）；值永远经 `platform.env` 读取。没有"在配置文件里写密钥"这条路。
5. **错误处理**：用户配置损坏 → 启动失败；项目配置损坏 → 整份忽略并警告（仓库里的坏文件不能阻塞会话，也不能生效一半）。

## 后果

- 零新增依赖；schema 即文档，错误信息可指出具体字段与来源文件。
- JSON 没有注释，配置的"写法示例与解释"必须放在文档而非文件模板里；若日后证明这是真实痛点，可在不改位置与 schema 的前提下换解析器（格式决策可逆性中等：换 JSONC 对既有文件向后兼容）。
- "环境变量合成 Provider 条目、按 id 参与合并"使 Phase 2 的纯环境变量用法与文件配置自然共存。

## 备选方案

- **JSONC / JSON5**：注释友好，但需要一个解析依赖（或自写 stripper，边界 case 易错）；在还没有用户抱怨之前不引入。
- **TOML / YAML**：更适合手写，但都引入新依赖且 YAML 的隐式类型转换有歧义风险。
- **配置放进 `.nocturne/` 之外的仓库根文件**（如 `nocturne.json`）：多一个顶层文件、多一个命名约定；统一收进 `.nocturne/` 更干净。
