# ADR-0064：定时任务——桌面端后台调度、无人值守非交互、每次运行一个会话

- 状态：已接受（维护者 2026-10-25 确认：应用关闭不触发、越权直接失败、每次运行新开会话、最小间隔 30 分钟）
- 日期：2026-10-25

## 背景

维护者希望 Nocturne 能按计划自动跑任务（例如每天早上汇总仓库动态、定时跑冒烟、检查依赖更新）。[agent-loop.md](../architecture/agent-loop.md) 第 5 节已写明：定时任务是产品功能，不进 Agent Loop，将来作为独立模块接入。它同时涉及常驻进程、权限、会话持久化和多个客户端，所以单独立 ADR。

参考了三家的本地定时任务（2026-10 文档与源码）：

| | Claude Code 桌面端 | Codex 应用 | ZCode |
|---|---|---|---|
| 何时触发 | 应用开着且电脑醒着，每分钟检查 | 本地任务需应用开着 | 「仅在电脑唤醒时运行」 |
| 错过 | 启动/唤醒时查最近 7 天，只补最近一次 | 未说明 | 未说明；失败有重试退避 |
| 每次运行 | 新会话；上一次没跑完就跳过并记原因 | 独立任务新会话进收件箱；对话里建的回原会话 | 对话里建的回原会话；同一任务单飞 |
| 无人值守权限 | 卡住等人批；可按任务「始终允许」 | `approval_policy = "never"`，越权直接失败 | 按任务保存权限模式 |
| 对话里创建 | 可以 | 可以 | `CronCreate` / `CronUpdate` / `CronList` |

三家的本地任务都不在应用关闭时触发，关机或关窗后要跑的场景交给各自的云端任务。Nocturne 没有云端执行，也不打算为此引入系统计划程序：**应用关着就不触发**。

## 决定

### 1. 调度器在哪里

- 调度器是 Core 里的独立模块（`packages/core/src/schedule/`），不依赖 UI；由 Runtime 选项 `scheduler: true` 启用，缺省关闭。
- **只有桌面端后台启用**（ADR-0051 的单后台，窗口打开期间常驻）。TUI、`nctrn -p`、`nctrn rpc` 的其他用法默认不启用，避免同一份任务被多个进程重复触发。
- 同一 `NOCTURNE_HOME` 下用锁文件保证至多一个调度器运行（沿用会话锁的做法，[ADR-0009](ADR-0009-session-lock.md)）；拿不到锁时调度器不启动并发出 `runtime.warning`，任务照常可以编辑。
- 窗口关闭即后台退出，调度停止。不做托盘常驻、开机自启或系统计划程序。

### 2. 任务定义

每个任务：

- `id`、`name`、`prompt`（指令正文）；
- `workspace`：工作区目录，或「普通对话」；
- `model`、`reasoningEffort`：缺省用当时的默认模型和档位；
- `permissionPreset`：缺省用当时的默认预设；
- `schedule`：`interval { minutes }`（每 N 分钟，N ≥ 30）、`hourly`、`daily { time }`、`weekdays { time }`、`weekly { day, time }`、`manual`（只能手动运行）、`cron { expr }`（五段，按本地时区）；最小间隔 30 分钟，`cron` 按相邻两次触发的间隔同样校验；
- `enabled`；
- `maxDurationMinutes`：单次运行的时长上限，缺省 60，到点按中断结束这一轮。

任务存放在程序维护的 `<NOCTURNE_HOME>/schedules.json`（与 `mcp.json` 同类：逐条校验、临时文件 + rename、同进程写入串行），不进 `config.json` 的分层合并。项目配置不能定义任务。

### 3. 每次运行

- 到点时调度器**新建一个会话**并提交 `prompt` 作为第一条用户消息；会话 `meta` 增加可选字段 `schedule: { taskId, scheduledAt, trigger: "schedule" | "catchup" | "manual" }`，客户端据此显示来源、归组。旧版本读到该字段时忽略（`meta` 未知字段的既有规则）。
- 同一任务上一次还在运行时，本次**跳过**，记一条跳过记录（原因 `previous_running`）。不同任务之间不互相阻塞，但同时运行的定时任务至多 2 个，超出的跳过（原因 `concurrency`）。
- 运行历史写 `<NOCTURNE_HOME>/schedules/history/<taskId>.jsonl`：每次触发一行（时间、触发方式、结果 `done | error | aborted | skipped`、跳过原因、会话 id）。保留最近 200 条。
- 「立即运行」是一次独立的手动运行（`trigger: "manual"`），不改动计划的下一次时间。

### 4. 错过的运行

后台启动时、以及检测到系统从睡眠恢复（两次检查之间的墙钟跳变超过 5 分钟）时，逐个任务检查最近 7 天内错过的计划时间：有的话**只补最近一次**（`trigger: "catchup"`），更早的丢弃并记为跳过（原因 `missed`）。补跑的会话开头的用户消息前附一行说明原计划时间，提示词需要按时间做判断的由用户自己写进 `prompt`。

### 5. 无人值守：非交互，越权直接失败

- 定时任务的会话以**会话级 `interactive: false`** 创建。Core 新增会话选项，复用现有的非交互实现：
  - 权限层：审查后的剩余 `ask` 一律 `deny(source: "non_interactive")`，不发 `permission.requested`；`smart` 的审查 allow 照常执行；
  - `ask_user`：立即以 `not_interactive` 结算，模型按默认继续并在最终回复里说明假设（[ADR-0032](ADR-0032-ask-user-tool.md) 第 4 节）；
  - 非交互拒绝的提示文案经 `nonInteractiveDenyHint` 注入：「这是无人值守的定时任务，无法请求确认；被拒绝的操作请在最终回复中列出，由用户之后处理」。
- 放行范围只来自任务的权限预设、手写规则和项目 Grant，不新增「按任务始终允许」的授权种类。需要更宽权限的任务，由用户给它选更宽的预设（例如 `bypass`）或写规则。
- 定时任务会话内**不提供**会修改定时任务本身的工具（见第 7 节），防止任务自我复制或改写自己。

### 6. 结果与通知

- 运行结束即普通会话，桌面端和手机端都能打开查看、继续对话。继续对话时会话恢复为交互（`interactive` 只约束调度器发起的那一轮）。
- 通知沿用 [ADR-0056](ADR-0056-session-notifications.md)：用户没在看时，出错和完成各提醒一次。因非交互拒绝导致任务没做完的，按普通完成或出错提醒，不新增事件。
- 侧栏把带 `meta.schedule` 的会话归入「定时任务」分组，按任务名分行。

### 7. 管理入口

- **桌面端**：新增「定时任务」页——列表（名称、计划摘要、启停、上次结果）、新建/编辑（字段同第 2 节）、立即运行、暂停/恢复、删除、运行历史（含跳过原因）。删除任务不删除它产生的会话。手机端经远程通道复用同一页面。
- **RPC**：`schedule.list`、`schedule.save`、`schedule.delete`、`schedule.runNow`、`schedule.history`；事件 `schedule.changed`（易失，列表或状态变化时通知客户端刷新）。
- **模型工具**：内置 `schedule` 工具（`list` / `create` / `update` / `pause` / `delete`），让用户在对话里说「每天 9 点做 X」即可创建。对话里建的任务与界面建的一样，每次运行新开会话，不回到创建它的会话；工具说明要求模型把运行所需的背景（关注的目录、输出格式等）写进 `prompt`。它声明为写入类工具，走常规权限层，按现有预设默认需要确认；声明新的 `ToolTraits.mutatesSchedule`，第 5 节的定时任务会话按该特性排除它（按特性筛选，不按工具名）。调度器未启用的进程里，该工具只返回「定时任务只在桌面端可用」。
- TUI、CLI 本版不提供管理界面。

## 兼容

- 新增 `schedules.json`、`schedules/history/`、会话 `meta.schedule`、会话级 `interactive` 选项、RPC 方法与易失事件 `schedule.changed`、工具特性 `mutatesSchedule`。不新增持久事件类型，不提升日志格式版本。
- 旧版本打开带 `meta.schedule` 的会话照常显示，只是没有来源标注。

## 不在本 ADR 内

- 每次运行用独立 git worktree（Claude Code、Codex 都有；先观察真实用法再决定）；
- 失败自动重试；
- 关窗后继续运行（托盘常驻、开机自启、系统计划程序）；
- 事件触发（Webhook、GitHub、邮件）。

## 验收

- 单元测试：计划解析与下一次时间（含 `weekdays`、`cron`、本地时区、夏令时边界）；最小间隔校验；错过补跑只补最近一次、7 天外丢弃；上一次未结束时跳过；并发上限；时长上限按中断结束；锁文件保证单调度器。
- 会话级非交互：定时会话里剩余 `ask` 被拒绝且不发 `permission.requested`；`ask_user` 以 `not_interactive` 结算；`smart` 审查放行仍执行；用户之后继续对话恢复交互。
- `schedule` 工具：普通会话需确认；定时会话里不可见；调度器未启用时给出提示。
- 桌面端：新建、编辑、立即运行、暂停、删除、历史与跳过原因、侧栏分组，附截图；手机端同页面可用。
- 回放：带 `meta.schedule` 的会话在新旧版本下都能打开。

## 后果

- 定时任务只在桌面端开着时跑，行为简单、可预期；代价是关机、关窗期间的任务只能补跑最近一次。
- 越权直接失败让任务结果确定、不会挂着等人，但需要用户事先给够权限；权限给宽了，无人值守时风险也更大——这一点在新建页的权限选择旁明确提示。
- 每次运行一个新会话，会话列表会变长；靠侧栏分组和归档缓解。

## 备选方案

- **系统计划程序（Windows 任务计划等）定时拉起 `nctrn -p`**：关窗也能跑，但要为每个平台各接一套，且维护者认为应用关着不需要触发。
- **卡住等人批准（Claude Code 的做法）**：能把事做完，但人不在时任务挂着，失去自动化的意义。维护者选择越权直接失败。
- **对话里建的任务回到原会话运行（Codex、ZCode 的做法）**：能沿用原会话的背景，但原会话每次运行多一轮、越跑越长，频繁压缩并丢失早先细节，还可能和用户正在进行的对话撞在一起。维护者选择统一新开会话，背景写进任务指令。
- **调度器放在每个 Runtime 里**：TUI 和桌面端同时开着时会重复触发；改为只在桌面端后台启用并加锁。

## 实现记录（2026-10-25）

权限主体（第 7 节「按现有预设默认需要确认」的落地，审查窗口选定）：

- 新增 `SubjectKind` `"schedule"`，不新增结构化字段。`detail` 复用现有的只读说明：多行纯文本（名称、计划、工作区、模型 · 档位 · 权限、指令全文）。桌面端与手机网页共用 `PermissionCard`，TUI 与 CLI 的确认提示都保留换行；长指令可以折叠，但能展开看全。
- `target` 是 `动作:任务名`。`create` 用任务名（如 `create:错误日志巡检`）；`update` / `pause` / `delete` 的入参只有 id（`permissionSubjects` 是纯函数，读不到任务名），所以用 id。会话 Grant 按 target 精确匹配，「本会话允许」只覆盖同一任务的同一动作。不提供 `allow_project`：Grant 不看指令内容，项目级授权会放行以后同名任务的不同指令。
- 全部交互式预设（含 `bypass`）追加 `schedule * → ask`，且 `userOnly`，所以 `smart` 不送审、直接问人。用户可写显式规则 `schedule * → allow` 放行。`--yes` 沿既有规则提升。
- 直接 `edit` `<NOCTURNE_HOME>/schedules.json`（及 `schedules/**`）同样至少 ask、`userOnly`，避免绕过 `schedule` 主体。与授权数据一样只是提示，`shell` 仍可绕过。

其余实现：

- cron 自己实现五段语法（`*`、数字、范围、步长、列表、月/星期三字母、星期 0/7 为周日、日与星期都限定时取或）。不引入依赖，也不支持 `@daily`、`?`、`L`、`W`、`#` 和秒字段。最小间隔看未来 800 天内的相邻触发。夏令时跟 JS `Date`。
- 恢复交互：定时会话的 `message.user` 少于 2 条时非交互（调度器的提交是第 1 条）；第 2 条是客户端提交，之后保持交互。只数日志事件，回退不删事件，所以重新打开结论不变。没有新事件。
- 「有非交互拒绝」：这一轮 `permission.resolved` 里 `source: "non_interactive"` 的条数，写入历史行的 `denied`。客户端不扫日志。
- 手机：`schedule.list`、`schedule.history`、`schedule.runNow` 在远程白名单；`save` 和 `delete` 只在本机。页面控件按这个禁用。

与 ADR 正文不一致的地方：无。`update` / `pause` / `delete` 的权限 target 用任务 id 而不是名称，原因见上。
