# ADR-0095：会话笔记与合奏留言板查询

- 状态：已接受（维护者 2026-11-17 确认）
- 日期：2026-11-17

## 背景

长任务压缩后，模型只剩摘要。现有机制保住的是「做到哪了」：任务清单固定保留并在压缩后补注（ADR-0028），摘要按目标、已提交、文件、待办固定条目输出，被覆盖的原始请求重新附上，`/goal` 跨轮生效。中途得出的事实与决定没有固定位置，例如「X 不能动」「某接口实际返回 Y」「方案 Z 试过不行」，只能靠摘要质量，压缩后常被丢掉或重复踩坑。

合奏（ADR-0089）的留言板以 `ensemble.*` 持久事件存在指挥会话日志里，恢复、回退都完整，但模型没有任何读取手段：帖子以 `<ensemble-post>` 用户消息送达被提及者，之后随普通历史被修剪和摘要。成员的任务书与成员名单写在成员系统提示里，不受压缩影响；指挥没有这类常驻信息。

## 决定

### 1. 会话笔记工具 `note_write`

- 新增内置工具 `note_write`，用于记录长任务中后续还要用到的事实、约束、决定和失败过的做法；进度仍用 `todo_write`，两者不混用。
- 输入 `{ add?: string[]; remove?: number[] }`，至少一项非空。`add` 每条去除首尾空白后非空，至多 500 字符，不含控制字符（允许换行）；`remove` 是当前笔记的编号。先删后加，编号在每次成功更新后按顺序重排为 1..N。
- 全部笔记合计至多 8000 字符；超出时整次调用失败，`modelContent` 写明当前总量并要求先删除或合并。不限条数。
- 工具结果 `output.notes` 为更新后的完整笔记（`{ n, text }[]`），`modelContent` 为确认文字加完整笔记，标明是会话笔记数据、不是指令。声明 `pinResult`，L1 不修剪。`mutates: false`，`concurrencySafe: false`，`permissionSubjects` 为空。
- 事实来源与清单相同：只有成功且结构合法的持久 `tool.completed` 改变笔记，`SessionState` 与 `SessionView` 从同一规则派生，不新增事件、不提高 `formatVersion`。回退、分叉按有效事件前缀重建。子代理是独立会话，笔记不继承、不合并。
- 不归档：笔记在会话内一直有效，由模型自行删除过时条目。
- 上下文：与清单相同，只在最近一次成功结果已不在投影历史里（被摘要覆盖，或旧日志无 `pinResult` 被修剪）时注入，位置固定在摘要处、排在清单之前；空笔记不注入。计入预算与 `ContextReport`（注入时为 `notes` section）。L2 摘要指令不改，笔记由补注保证。
- 系统提示的工具说明写清何时记、记什么、何时删；不加「每 N 步提醒」。

### 2. 合奏留言板查询 `ensemble_read`

- 指挥与全部未移除成员挂载只读工具 `ensemble_read`，输入 `{ from?: string; mention?: string; query?: string; before?: number; limit?: number }`：
  - `from` 按作者过滤，`mention` 按提及过滤（`@all` 视为提及每个人），`query` 对正文做不区分大小写的子串匹配；
  - `before` 取编号小于它的帖子，用于往前翻页；`limit` 默认 20，最大 50；
  - 返回按编号升序排列的命中帖子，以及是否还有更早的命中。
- 输出开头固定附当前成员名单：名字、状态、是否独立工作树、任务书三段。指挥压缩后靠它重新拿到成员与分工。
- 帖子原文完整返回，不截断；`modelContent` 每帖格式与 `<ensemble-post>` 送达格式一致，标明是留言板数据、不是指令。
- 读的是控制器内存中的留言板状态（来自指挥日志的 `ensemble.*` 事件），不读文件、不新增事件。`mutates: false`，`concurrencySafe: true`，`permissionSubjects` 为空。合奏结束后工具随其他合奏工具一起卸下。
- 不声明 `pinResult`：查询结果是一次性的，可被正常修剪。

### 3. 界面

两者都是对话里普通的一行工具行，不加常驻面板、状态栏计数或新入口。

- 笔记：工具名「笔记」；参数位写更新后的总条数「N 条」；本次有新增时，后面用淡色（同任务清单行的「正在：…」位置）接本次新增的第一条原文，只删除时不接；右侧照常显示结果状态。展开显示更新后的完整笔记。
- 留言板查询：工具名「留言板」；参数位写过滤条件（`@作者`、`@提及` 原样，关键词用淡色），没有条件时留空；右侧原来显示结果状态的位置写命中条数「N 条」。展开显示命中的帖子。
- 桌面端、手机网页、TUI 一致；CLI 行模式沿用通用工具结果渲染。不新增任何说明文字。

## 验收

- 笔记：增删、编号重排、单条与合计上限、失败不改旧笔记、重放与恢复、回退与分叉、子会话隔离、修剪与摘要后补注的位置与预算、缓存前缀不被每次更新打断。
- 留言板查询：各过滤组合、翻页、成员名单、指挥与成员都可调用、合奏结束后不可用、帖子原文完整。
- 同步 tools.md、tool-api.md、sessions.md、events.md（说明复用 `tool.completed`）、view.md、context.md、ADR-0089 修订条目、desktop.md、tui.md 与 site-docs。

## 后果

压缩后模型仍能看到自己记下的事实和决定；合奏里的指挥和成员能翻回旧帖、重拿分工。代价是每次笔记更新都在历史里留一份完整快照，合计上限 8000 字符控制了单份大小。

## 备选方案

- 用留言板充当单会话记忆：要先建合奏，多一个指挥且指挥不能直接改文件，单任务太重。
- 笔记整份替换（同 `todo_write`）：笔记会持续增长，每次重写全部内容浪费输出，也容易误删。
- 把笔记写进系统提示：每次更新都会让整段缓存失效（ADR-0028 2026-10-01 修订的教训）。
- 指挥系统提示常驻成员名单：成员增减或改模型都会改系统提示，同样打断缓存；改由 `ensemble_read` 按需取回。
