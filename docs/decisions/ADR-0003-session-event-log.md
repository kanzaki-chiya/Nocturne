# ADR-0003：追加式事件日志作为会话唯一事实来源

- 状态：已接受（第 2 版，2026-09-23）
- 日期：2026-09-23

## 背景

会话需要支持：实时流式显示、退出后恢复、崩溃恢复、审计、将来多客户端观察。参考项目的做法：

- **ZCode**：持久事实存储是 SQLite 中的 session / message / part / session_entry / session_input 等表（Message + Part 结构与 OpenCode 同形）。实时会话事件由内存事件存储分配序号并推送，临时事件按 Turn 窗口淘汰；部分事件类型经 `persistDurableSessionEvent`（`core/src/runtime/methods/events.ts`）写入 session_entry、session_input 等表。冷恢复时从持久消息合成展示事件（`synthesizeEventsFromMessages`）。持久存储本身是清楚的事实来源，问题在于**实时路径与冷恢复路径经过不同的投影过程**，代码中大量"冷热同形"的注释说明，维持两条路径行为一致的成本很高。
- **Codex**：会话持久化为追加式 JSONL rollout，包含会话元数据、模型可见的响应项、压缩记录与部分事件；恢复时从 rollout 重建历史。
- **OpenCode**：Session → Message → Part 模型，存储在数据库中，实时通过事件总线推送部分更新。

## 决定

1. 每个会话一条追加式 JSONL 事件日志，这是会话的唯一事实来源。
2. 事件分为**持久化事件**（完整消息、工具调用开始与结果、权限决定、压缩、配置变化、Turn 边界）和**临时事件**（文本增量、进度、状态）。只有持久化事件写入日志。
3. **序号**：持久化事件独占会话内从 1 连续递增的 `seq`；临时事件使用本次运行的 `runId` 与运行内序号，不占用 `seq`。恢复后从日志中最后一个有效 `seq` 继续，无需额外的高水位记录。
4. **先写后发、先写后执行**：持久化事件写入成功后才分发；`tool.started` 写入成功后工具才执行。写入失败时会话进入 `failed` 状态，停止一切推进。
5. **打开顺序**：取得排他锁 → 读取校验 → 截断损坏尾部（仅最后一行，先另存）→ 中间损坏则拒绝打开 → 追加修复事件 → 开放。
6. **修复**：为所有未结算的工具调用与未结束的 Turn 追加修复事件，检查范围是整条日志。
7. **持久性承诺**：进程崩溃级；不承诺断电级。
8. `SessionState` 与模型上下文都由持久化事件派生；不维护第二份消息存储。MVP 不做快照。

细节见 [sessions.md](../architecture/sessions.md) 与 [events.md](../protocols/events.md)。

## 后果

- 恢复、审计、回放都读同一条日志，实时状态与恢复状态由同一个折叠函数产生，减少了"两条投影路径"的维护成本。但这**不等于**不会出现不一致：折叠逻辑的缺陷、格式版本兼容、修复规则错误仍可能导致问题，需要测试覆盖（截断日志、中间损坏、未结算调用、版本不匹配）。
- 文本增量不持久化，崩溃时正在输出的文本会丢失（可接受：它尚未成为完整事实）。
- 新增持久化事件类型会使旧版本 Runtime 无法恢复包含它的会话（[events.md](../protocols/events.md) 第 8 节）。
- 列出会话、跨会话查询需要读取多个文件；规模变大时加入可重建的索引。
- 需要实现锁、尾部截断、写入失败处理，这是选择文件日志必须承担的恢复义务。

## 备选方案

- **消息表 + 内存事件**（ZCode）：查询方便；代价是实时与冷恢复两条投影路径。
- **SQLite 作为 MVP 存储**：事务、并发与查询更强，锁和尾部损坏问题由数据库处理；但需要迁移体系，且对 MVP 的顺序追加与顺序读取收益有限。事件模型不依赖存储介质，以后可以替换 `SessionStore` 实现。
- **所有事件共享永久序号**：需要持久化序号高水位或在恢复时跳号，复杂度更高且收益不明显。
- **持久化全部事件（含增量）**：日志体积大幅增加，恢复时需要重新合并增量。
