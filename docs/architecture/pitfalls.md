# 架构陷阱清单

> 状态：已接受 v0.2 ｜ 用途：设计评审与代码评审时对照 ｜ 证据来源：[research/zcode-review.md](../research/zcode-review.md)

每条包含：为什么危险、早期症状、Nocturne 的规避方式。评审时若发现某条的早期症状，应在合并前处理或记录为明确的技术债。

## A. 运行时结构

### 1. UI 与 Runtime 耦合
- **危险**：每新增一个客户端都要复制一遍 Agent 逻辑，行为逐渐分叉。
- **症状**：Core 里出现 spinner、颜色、终端宽度、"desktop"之类的概念；客户端里出现会话状态或权限判断。
- **规避**：Core 只收命令、发事件（[ADR-0002](../decisions/ADR-0002-ui-independent-core.md)）；依赖检查禁止 Core 引用客户端；客户端之间只允许共享 `protocol` 中的纯函数。

### 2. 巨型 Agent 类
- **危险**：所有状态和方法堆在一个对象上，任何修改都可能影响无关行为，无法单独测试。ZCode 的 `AgentRuntime` 有约 80 个私有字段，方法通过混入分散在上百个文件中。
- **症状**：Runtime 类字段超过十几个；新功能的第一反应是"给 Runtime 加个字段"。
- **规避**：Agent Loop 无状态，状态归会话；上下文、工具、权限、Provider 各自是独立对象，通过窄接口注入。

### 3. 工具特判
- **危险**：每加一个工具就要修改循环、权限、调度等多处代码。
- **症状**：出现 `if (tool.name === "shell")`，或按工具名维护的集合（如"只读工具列表"）。
- **规避**：差异全部写在 `ToolDefinition` 的声明中（[tools.md](tools.md)）；代码评审拒绝按名字分支。

### 4. Provider 特判
- **危险**：新增一个模型服务要改动 Core；模型行为差异泄漏到上下文构建和循环中。
- **症状**：Core 中出现 Provider 名称字符串比较，或 Provider 专有字段。
- **规避**：适配器内归一化，差异表达为能力数据（[providers.md](providers.md)）。

### 5. 权限判断散落
- **危险**：安全边界无法审计，某条路径忘了检查就是漏洞。
- **症状**：工具内部自己弹确认；UI 根据工具类型决定是否提示；"yolo"标志被层层传递。
- **规避**：权限只在执行管线的权限步骤判定（[tools.md](tools.md) 第 3 节）；工具只声明主体。

## B. 状态与数据

### 6. 上下文无限增长
- **危险**：长任务必然撞上窗口上限，或者成本失控。
- **症状**：把会话历史直接当作请求消息数组；工具输出不设上限。
- **规避**：会话历史与模型上下文分离；每项注入内容有上限；压缩以事件记录（[context.md](context.md)）。

### 7. 会话无法恢复
- **危险**：崩溃或退出后任务丢失，用户不敢把长任务交给 Agent。
- **症状**：关键状态只存在内存；恢复需要"猜"上次执行到哪里。
- **规避**：追加式事件日志是唯一事实来源，先写后发，恢复时显式修复未完成的 Turn（[sessions.md](sessions.md)）。

### 8. 实时路径与恢复路径各有一套投影
- **危险**：实时状态由一条路径产生，恢复后的状态由另一条路径产生，两条路径的行为必须人为保持一致，任何一侧的修改都可能让"运行中看到的"与"重启后看到的"不同。ZCode 的实时事件在内存中推送，冷恢复时从持久消息合成展示事件，大量代码注释在处理"冷热同形"。
- **症状**：出现"从 A 重建 B"的同步代码；同一个字段在两处各写一次；某个显示问题只在重启后出现。
- **规避**：实时与恢复使用同一条持久化事件流和同一个折叠函数（[ADR-0003](../decisions/ADR-0003-session-event-log.md)）。这降低但不消除风险：折叠逻辑、版本兼容与修复规则仍需要恢复场景的测试。

### 9. 事件不结构化
- **危险**：客户端只能解析文本，无法可靠渲染、回放或审计。
- **症状**：事件载荷是自由字符串；用错误信息文本判断错误类型。
- **规避**：事件有明确的类型与字段（[events.md](../protocols/events.md)）；错误以 `kind` / `code` 区分。

## C. 文档

### 10. 代码成为唯一文档
- **危险**：设计意图丢失，后来者只能从实现反推，架构被动地适应既有代码。
- **症状**：评审时回答"看代码就知道"；重要决定只存在于聊天或 issue 中。
- **规避**：行为变化必须同步文档（[workflow.md](../development/workflow.md)）；难以逆转的决定写 ADR。

### 11. 文档重复
- **危险**：同一内容多处维护，必然有一处过时，读者不知道信哪一份。
- **症状**：README、AGENTS.md、模块 README 中出现相同段落。
- **规避**：一个概念一个主文档，其他地方一句摘要加链接。

### 12. 文档长期失效
- **危险**：错误的文档比没有文档更糟，尤其会误导 Coding Agent。ZCode 的 `apps/zcode-cli/README.md` 仍描述"运行时零依赖、`src/cli` 目录结构"，与实际的多包结构不符。
- **症状**：文档提到的文件或命令已不存在。
- **规避**：变更检查清单包含文档；定期用脚本检查文档中的路径与链接是否存在。

### 13. AGENTS.md 变成巨型说明书
- **危险**：每次对话都加载，挤占上下文，且与正式文档重复。
- **症状**：AGENTS.md 超过一两屏，出现设计细节。
- **规避**：只保留规则与阅读指引，细节链接到 docs/。

### 14. Agent 每次读取整个 docs/
- **危险**：浪费 token，并把无关内容带入决策。
- **症状**：Agent 的第一步是列出并读取所有文档。
- **规避**：文档按层级组织，索引与 AGENTS.md 提供按任务的阅读清单；研究记录单独存放并注明按需阅读。

## D. 过早与过度

### 15. 过早 Multi-Agent / Swarm
- **危险**：在单 Agent 的会话、上下文、工具还不稳定时引入编排，问题相互放大。
- **症状**：出现"Agent 之间的消息总线""角色系统"等设计。
- **规避**：Subagent 放在 Phase 6，定义为"一个工具启动一个受控子会话"（[subagent.md](subagent.md)）：子会话是普通会话、衔接点是普通工具调用，编排/角色/总线仍不做。

### 16. 过早 RPC / Desktop
- **危险**：协议一旦对外就难以修改，而此时核心语义还在变化；ZCode 同时维护两代协议即是代价。
- **症状**：在只有一个进程内客户端时就设计传输层、断线重连。
- **规避**：先让进程内 API 稳定；公开 API 的语义与将来的 RPC 一致，但传输层推迟。

### 17. 过度拆包
- **危险**：包之间的版本、构建、导出维护成本超过收益。
- **症状**：一个包只有一两个文件；为了"以后可能复用"而拆包。
- **规避**：起步只有 `packages/core` 与 `apps/cli` 两个包，拆包条件见 [repository-layout.md](../development/repository-layout.md)。

### 18. 过度抽象与为假想需求设计
- **危险**：抽象层增加理解成本，却没有第二个实现来验证它是否合理。
- **症状**：接口只有一个实现且看不到第二个；配置项没有使用者。
- **规避**：只为已有的两个以上实现或路线图中已排期的需求建立抽象；其余保留接入点即可。

### 19. 照抄参考项目的历史架构
- **危险**：继承了别人的历史包袱，却没有别人的历史理由。
- **症状**：理由是"ZCode / Claude Code 也这么做"。
- **规避**：借鉴必须说明它在 Nocturne 中解决什么问题；参考 [research/zcode-review.md](../research/zcode-review.md) 的分类。

### 20. 权限预设膨胀为"模式"
- **危险**：每种模式在代码里一套分支（ZCode 有 build / edit / plan / yolo / auto，且 auto 标注"未实现"），组合爆炸。
- **症状**：权限代码中出现 `if (mode === ...)`。
- **规避**：预设只是规则集合；计划模式之类的行为属于 Agent 层，不属于权限。
